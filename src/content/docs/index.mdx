## From the trenches: why this guide exists

I wrote this guide out of frustration with AI demo hype and the messy reality of production engineering.

I am Glen Keane. Over the past decade, I have worked across high-throughput distributed systems and performance tooling (former Node.js core collaborator, co-maintainer of `autocannon` with Matteo Collina, nearForm, and Wayflyer). Today, I work forward-deployed at Brightbeam, building enterprise AI systems and claims automation for clients like AXA and Zurich.

When engineers use AI coding assistants for serious work, they hit the same wall: the **80% calculator trap**. An adding machine that calculates correctly 4 times out of 5 does not automate your work; it doubles your anxiety. If you have to babysit every token in an editor, you suffer review fatigue and end up rubber-stamping code you do not understand. That is how comprehension debt explodes.

The solution is not "prompt engineering", larger context windows, or another proprietary SaaS framework. The solution is boring, disciplined software engineering:

1. **Be the Product Manager of your own tools**: You define high-level intent, constraints, and acceptance criteria. You never micromanage internal model generation.
2. **Mechanical test gates**: Untrusted assistant code runs in isolated git worktrees. If it fails a deterministic test gate or linter (exit code 0), it never touches your branch.
3. **Disposable micro-tools**: When a routine friction point repeats, have the assistant build a focused tool. *If a tool works, you keep it. If it breaks or stops serving you, you either refine it, or these days, it is getting cheap to throw it away and build the next one in an afternoon.*

This guide teaches the mindset, architecture, and daily mechanics of building with autonomously self-improving tooling. No corporate fluff, no paywall, 100% open source.
