## Start with a failing case

Take one workflow you already run. Before adding another helper, write a small input that should stop it. For a support-ticket report, use a repeated ticket ID, an old export timestamp and refund rows in two currencies. These are constructed cases, not measured results.

Write the expected behaviour beside each fixture. A repeated ID holds the report. A stale export is rejected against a freshness policy agreed with its owner. EUR and USD totals stay separate unless an explicit conversion rule exists. Put those checks before grouping or drafting.

Then test the whole run: interrupt it before and after delivery. A draft needs approval for its exact content and recipients. If delivery is ambiguous and the provider cannot deduplicate, hold for reconciliation instead of blindly sending again. [Run it for real](../../journey/07-run-it-for-real/) develops that plan.

Start with one of these failures, prove the check catches it and keep a clean case passing. “Think big, act small” applies to the harness too.

## Where "harness" is defined

A [harness](../../glossary/#harness) is the program around the assistant: the part that runs tools, applies permissions and keeps logs. Level 3 defines it at first use. The shelf is the engineering view of it.

<summary>Tool versions and source checks</summary>

The journey is written for any reader. The mechanism that engineers care about sits in the Expert corner and the Go deeper blocks of each level. Read those first, then the shelf.

The shelf is written against Claude Code, with notes on Codex CLI. The ideas transfer; the setting names do not. Each page names the tool, the docs page fetched and the date. Each verification line gives the installed Claude Code version; the docs pages state no version of their own. Look for the line that starts "Docs page fetched on". A page that could not be fetched says `Not checked against current docs`, and a claim without either line is generic.
