## The idea

**A job with many steps fails more often than any one of its steps, so you measure it, record it and put limits on it.** Three ideas make a job safe to leave alone:

- **Reliability maths** tells you how often a many-step job succeeds, and which step to fix first.
- **An [audit log](../../glossary/#audit-log)** is a written record of every step, so you can see what happened afterwards.
- **Limits** cap time, spend and retries, so a bad run stays small.

### Why many steps hurt

Small error rates multiply along a chain. This is **[compounding error](../../glossary/#compounding-error)**. A job of ten steps, each right 95 times in 100, comes out fully right about six times in ten. One weak step at 80 in 100 pulls that to about five in ten. The numbers are made up; they do not measure any real system.

A check on the weak step, and a retry, win runs back. The [evals](../../glossary/#eval) from level 5 are the tool for real numbers: count per step, so you know which one is weak. Thirty clean runs in a row mean the failure rate is probably below about 1 in 10 (the rule of three: 3 divided by 30). A few good runs prove little.

<details class="go-deeper">
<summary>Go deeper, for people who write code: what a check on the weak step buys</summary>

A check catches 90% of a step's errors. If the retry always works, a step right with chance p becomes p + (1 - p) x 0.90. If the retry works half the time, it becomes p + (1 - p) x 0.45. Case C checks the weak step only. Case D checks every step. The numbers are made up. The same sums work in a spreadsheet. The code uses `python3 -I`. `-I` makes Python ignore environment variables and the current folder when it imports modules. It does not stop Python reading files, and it does not make results identical on every machine.

<Example

for retry in (1, 0.5):
    weak = 0.80 + 0.20 * 0.90 * retry

    print(retry, round(p * weak, 3), round(good**9 * weak, 3))"
```

```

</Fragment>

</Fragment>

### The audit log

When the run goes odd on Friday, you need to see what each step did. An audit log is one line per step, written as the step happens, with the time first and one [run identity](../../glossary/#run-identity) (a string made once at the start) on every line. Each line holds the result in a few words, the check result, the time taken and the cost. It holds no full documents and no personal data.

  task="Sam reads the log of a month-end run that stopped, to find which step made the duplicate month."

<Fragment slot="input">

```

</Fragment>

<Fragment slot="output">

t=2026-10-02T09:14:14Z run=2026-10-02-0412 step=stop      status=held waiting_for=human
```

</Fragment>

<Fragment slot="notice">

The read line says `months=9` and the calculate line says `months=10`, so the duplicate was made at calculate, not read. The check failed and the run held for a person.

</Fragment>

### Limits

A run with no limits can run forever or spend without bound. Set these before you leave it alone:

- **Time cap.** A step that takes longer than a set time, say 120 seconds, counts as failed.
- **[Spend cap](../../glossary/#spend-cap).** A run stops when it has used its budget of paid usage.
- **Step cap.** A run stops after a fixed number of steps, so a loop cannot go round forever.
- **Bounded [retries](../../glossary/#retry).** A failed step may retry at most twice, with a pause that grows. Then it stops and reports.

:::tip[New to this]
A **retry** helps when the failure was a hiccup, such as a slow network. It cannot fix a wrong input. That is why you cap retries and add a check.
:::

## Under the bonnet

*How it works. Optional reading.*

Reliability maths only works if steps fail independently. They do not always: if the first step reads the wrong file, every later step is wrong in the same direction. Treat the multiplication as a rough guide to which part of the chain is fragile, then measure. A stranger should be able to answer "what happened in run 0412?" from the audit log alone. For engineers: [cost and resources](../../shelf/operations/cost-and-resources/).

<details class="go-deeper">
<summary>Go deeper: restart after a failure</summary>

If the run dies after step 6 of ten, a rerun from step 1 costs time and may repeat side effects (changes outside the run, such as a sent message). A run you can leave alone has these properties:

1. **Each step saves its output** to a named place, with the run identity. Write to a temporary file, then rename it, so a crash never leaves a half-written file that looks complete.
2. **On restart, the run finds the last completed step** and resumes from the next one.
3. **Steps with side effects are [idempotent](../../glossary/#idempotent)**: safe to do twice, or they check a record first ("did I already send this?"). Reading and calculating usually are. Sending and paying usually are not.
4. **Steps that cannot be undone sit behind a human checkpoint**, after the checks, as in level 4.
5. **A half-finished run says so**, with a status such as "stopped at step 6, waiting".

If Mina's run dies after the calculate step, the restart skips reading and calculating and runs the check on the saved totals. Nothing was sent, because sending is the last step, behind a checkpoint.

</details>

:::note[At work]
In a finance close this is the close checklist with completed-by and date columns, and a posted-journal reference that stops double posting.
:::

## Expert corner

:::caution[Expert corner]
A cheap deterministic check (a count, a schema, a sum against the bank statement) is a better first check than a second model asking "does this look right?". Principle, not measured: a check that shares the producer's model and prompt shares its blind spots. In the guide's one reviewer test a same-context reviewer matched a fresh one (see [level 5](../05-check-the-work/)).

Retrying a deterministic wrong answer burns spend; retrying a timeout is sensible. Cap total attempts per run, not only per step. Idempotency keys make a restart safe where the provider drops repeated keys. Where none exists, a crash between the send and the log can send twice.
:::

## Agent note

:::note[Agent note]
**Topic: running many steps with a log and limits.**

If no cap is given for a multi-step run, ask for one before you start. Ask once per task, in one message, with every open item and your default for each (at most five items). If nobody can answer, state your assumptions and carry on with read-only work. Take no action that changes something. Use a run identity: a string you generate once at the start and reuse on every log line.

Write one audit log line per step, as the step completes. Put `t=` first, in UTC with seconds. Include the run identity, step name, status and a short reason on failure. The harness writes the duration and the cost. Do not log secrets or full personal data.

Enforce the time, spend, step and retry caps given to you. When a cap is reached, stop and report. Do not extend a cap yourself.

Retry only failures that look transient. Do not retry a failed check. Retry at most the number of times you are told.

Before a step with a side effect outside the run, check whether it already ran for this run identity. If it did, skip it. On restart, resume from the last completed step and report it.

Check: after any run, the log lets someone name the step that produced a given output.
:::

## Mistakes people make

**Trusting the average step.** Each step looks fine, so the job looks fine. Fix: multiply, then find the weakest step. Put a check there first. Measure with known cases, as in level 5.

**Logging nothing, or everything.** With no log, Friday is a mystery. A full transcript is never read and holds data it should not. Fix: one short line per step, with status, reason, duration and cost.

**Setting no limits because "it has never run away".** The first runaway costs real money or sends one message forty times. Fix: set the four caps first, and put anything irreversible behind a human checkpoint.

**Self-test**

1. A five-step job has every step at 90%. Roughly what share of runs are fully right, and what is the first thing you would do about it?
2. Mina's run stopped after the check failed. The log's read line shows `months=9`, and the duplicate month first appears at the calculate step. Where do you look, and where do you not?
3. A run sends a summary email as its final step, then crashes while writing the log. You restart it. What must be true so Mina does not get two emails?

<details>
<summary>Answers</summary>

1. 0.9^5 = 0.59, about six in ten. Find the weakest step by counting on known cases, then add a check there.
2. The read line shows `months=9`, so look at the calculate brief and its inputs, not the export. The log has narrowed the search.
3. Write the intent record before the send, and send with a key the provider uses to drop repeats. If none exists, a crash can send twice, so keep the send behind a human checkpoint.
