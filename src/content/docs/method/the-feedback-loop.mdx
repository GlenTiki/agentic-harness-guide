**Status.** Built in the case study: the retro format, a parser and a proposals file ([chapter 9](../../case-study/ch09-retro/)). Runs in my setup: only the correction-to-memory loop and a stop-time reminder. Design only: a full praise-first retro run by the [agent](../../glossary/#agent), and learning from your behaviour beyond a small boost in search ranking.

## Be honest about what exists

My setup does not have a praise-first retro. Here is what it has.

1. When I correct the agent, it saves a short memory note. A later hook brings that note back when it is relevant.
2. A stop-time hook makes the agent scan the session once and save what it learned.
3. A short ring buffer of session summaries tells the next session what to pick up.
4. You can promote a rule that keeps breaking into the always-loaded instructions.

That is a correction loop. It records and reinforces. It does not adapt its own thresholds from your history, and it does not ask you what went well. The case study builds the retro as a plain-text format, so you can try it without any of my setup.

## The four parts

Start with what went right. Then describe what went wrong in three parts.

1. **What went well.** Name what worked, so nobody breaks it later. "The plan came before the edit" is worth saying out loud.
2. **What it was.** Say what the work was. One sentence. "The month-end summary."
3. **What happened.** Describe what you saw, not what you guessed. "The total included February twice."
4. **What I preferred.** Say what you wanted instead. "A stop with a message, and the count of months."

Praise comes first for a practical reason. A fix can break something that worked. If you name what worked, the agent has a list of behaviours to protect. I also think it keeps the tone of the exchange useful, but I have not tested that.

## From retro to fix

A proposal is the start of the [weak-spot loop](../engineer-weak-spots/). The first proposal above names a weak spot ("a month can be counted twice"). It engineers a check, and it asks for a proof that the check can fail. The retro supplies the notice and the name. The loop supplies the rest.

## A worked loop

This is a Constructed trace of two retros on the same feature, with one proposal accepted, one rejected and one stalled. It is invented for teaching. It is not a recorded run, and it uses the four parts above.

<Example
  label="Constructed"
  task="You read the proposals from a retro and decide each one, with a reason you can look up later."
  evidence="none, written by the author"
  env="not a model output"
>

<Fragment slot="input">

```text
Retro, week 1. Proposals returned by the agent:
P1  Add a distinct-month check before any total. Prove it fails on a list with February twice.
P2  Ask a second person to approve every note to Mina.
P3  Ask you for one sentence in your own voice for Mina notes.
```

</Fragment>

<Fragment slot="output">

```text
Decisions
P1  Accepted. Check written, seen failing on the February list, then passing. Rule added: "Count distinct months before any total."
P2  Rejected. Reason: it slows every note for a problem seen once. Revisit if the stiff wording is reported a second time and P3 has not fixed it.
P3  Accepted, not yet done. Owner: you. Needed: one sentence.

Retro, week 2
Went well: the distinct-month check stopped a repeated March.
What happened: the note to Mina was stiff again.
Decisions: P3 is still waiting for the sentence. P2 trigger is met, so it is reopened.
```

</Fragment>

<Fragment slot="notice">

P2 carries its reason and its reopening condition, so week 2 can act on it without a new argument. P1 has a check seen to fail. P3 has an owner and a named missing item.

</Fragment>

<Fragment slot="shows">

It shows a loop with a decision and a reason for each proposal. It does not show how often retros produce proposals this clean.

</Fragment>

</Example>

## When the loop itself fails

The worst failure is quiet: feedback is given, recorded and acknowledged, and no rule changes. The next trace shows it.

<Example
  label="Constructed"
  task="You scan four weeks of retro lines to see whether any feedback changed a rule. The log is invented for teaching. It is not a recorded run."
  evidence="none, written by the author"
  env="not a model output"
>

<Fragment slot="input">

```text
week 1  What happened: note to Mina was stiff.      Rule changes this week: 1 (distinct months)
week 2  What happened: note to Mina was stiff.      Rule changes this week: 0
week 3  What happened: note to Mina was stiff.      Rule changes this week: 0
week 4  What happened: note to Mina was stiff.      Rule changes this week: 0
```

</Fragment>

<Fragment slot="output">

```text
Diagnosis
The same "what happened" line appears 4 times. The only rule change is for a different problem.
The proposal for it (P3, one sentence from you) has been waiting since week 1, with no owner date.
Fix: give P3 a date, or decide not to fix it and say so. A complaint that repeats with no decision is a failed loop.
```

</Fragment>

<Fragment slot="notice">

The retro was held every week and nothing improved, so holding it is not the measure. The measure is the link between a repeated line and a change.

</Fragment>

<Fragment slot="shows">

It shows how to spot a loop that records and never acts. It does not say how many repeats to allow. Three is a reasonable starting value to tune on your own log.

</Fragment>

</Example>

Keep a count in the retro log of lines repeated without a decision. If it is not zero at the end of the month, deal with that before you add anything new.

## Eventually consistent with what you want

I use the phrase "eventually consistent" in its plain meaning. After many loops the system should settle on what you want, even though any single run may be wrong. Three signals suggest it is settling:

- Fewer corrections per feature.
- Checks that went red once now stay green.
- The same slip stops coming back.

This is a hope, not a result. I have no measurements for my own setup. The case study gives you the pieces to measure it for yourself: the retro log, the event log and the freshness check in [chapter 10](../../case-study/ch10-monitor/).

## What the agent must not do

- It must not skip the praise and start with faults.
- It must not change the instruction files or memory without your yes. Show the change first.
- It must not report a fix as done until the check has been seen to fail and then pass.
