*For a person who directs agent work and has handed an agent a task list at least once, arriving from the Next line of the weak-spots page or from the end-to-end flows and orchestrator setup pages. You leave with a split of jobs, the outcome yours and the plan the agent's; without it, you write the steps yourself and correct the agent after the edit instead of before it. An agent reading this page should not run any command here unless the user asks.*

**Status.** Runs in my setup: the lead-agent pattern, the delegation counters and the plain-English briefs. Design only: personas that keep their own memory (see [personas](../../setup/personas/)). The benefits listed under "Hypotheses" are not measured.

Some people give an [agent](../../glossary/#agent) a task list. My working practice is a different split. You say what you want and how you will know it works. The agent works out the steps. You watch, step in, and add context when the agent drifts. I think this saves rework, but I have not measured it.

## Two jobs, not one

| Role | Who | What they own |
| --- | --- | --- |
| Product manager | You | The outcome, the expected behaviour in plain English, the yes or no on anything outside the working files |
| Tech lead | The lead agent | The plan, the split into tasks, the briefs for helpers, the checks, the report back to you |
| Helpers | [Sub-agents](../../glossary/#sub-agent) | One bounded task each, then a short report |
| Expert viewpoints | Simulated personas | One review lens each, such as security or the reader of the final page |

In my experience the lead agent is faster at the typing and worse at knowing what you meant. Your job is to close that gap with words, not with code.

## What you say

Describe the outcome and the expected behaviour. Skip the how. End with "tell me your plan before you start". That makes the agent explain its next step, so you can correct it before it acts. In my experience one such exchange usually costs less than undoing a wrong edit.

## You may ramble

You do not need a tidy brief. You can think out loud and change your mind. A good lead agent turns that into questions, and a question budget keeps it short: one message, every open item, a default for each.

## Monitor, step in, keep adding context

While the work runs, watch three signals.

1. **The plan.** Does the next step match what you meant?
2. **The checks.** Did a check run, and did it go red when it should?
3. **The record.** Is there a log of what the agent did, so you can read it later?

When the agent drifts, do not restart. Add the missing fact in a sentence and say "carry on". In my experience the agent keeps what it has already learned, so you pay for one correction and not a fresh start. I have not measured this. If the same drift happens twice, treat it as a weak spot and run the [five-step loop](../engineer-weak-spots/#the-loop): notice, name, engineer a fix, prove the fix can fail, keep it.

## Why the lead can keep one long thread

Helpers do the bulky reading and return a short report. The lead keeps the plan and the reports, not the raw files. This is why I expect a lead agent to stay in one thread for longer. It is a design intent, not a measurement. See the hypotheses below.

## For engineers: what helpers inherit

In plain terms: rules you set up outside the assistant also apply to its helpers. The rest of this section is for readers who build or configure agent harnesses, and you can skip it. It lists what each helper inherits, because people often guess wrong.

- **Hooks apply to helpers.** A hook runs for tool calls made by a helper in the same way as for the main thread. The hook input identifies the helper.
- **Project instructions apply, with exceptions.** Custom helpers load the project instruction files. The built-in read-only Explore and Plan helpers skip them. A custom helper can opt out with a setting.
- **Helpers can start helpers.** By default a helper can start its own helpers, up to three layers below the main thread. An environment variable turns this off.

My own rule is stricter than the tool allows. In my setup a helper returns its findings and the lead starts the next helper. I keep one layer on purpose, because a flat layout is easier to read in a log. That is a choice, not a limit of the tool.

One more fact matters. My setup also has its own helper launcher that builds a helper from a role file. That launcher gives the helper no hooks and no project instructions. Only the native helpers of the host tool inherit them. The [hooks page](../../setup/hooks/#what-subagents-inherit) explains the difference.

## Hypotheses

I believe these. I have not measured them. Treat each one as a claim to test.

1. **Hypothesis: the lead's context stays smaller.** Test: compare the [token](../../glossary/#token) count of a long task done with helpers and the same task done in one thread.
2. **Hypothesis: you correct less often.** Test: count your corrections per feature over ten features, with and without the plan-first rule.
3. **Hypothesis: a plan shown before action catches a wrong reading early.** Test: count how many plans you edited before the agent acted.
4. **Hypothesis: simulated experts find problems a single reader misses.** Test: seed a known defect and see which persona finds it.

If a test fails, change the practice. That is the [weak-spot loop](../engineer-weak-spots/) applied to the method itself.
