The case study rebuilds the ideas in the [setup pages](../setup/) from nothing. It wraps a tiny plain-text notes tool in a small harness kit. Each chapter removes one [weak spot](../method/engineer-weak-spots/), and each chapter has a check that you can see go red.

**Status.** Built in the case study, with one exception: chapter 8 is Design only, with a small working scaffold. Every command and output on the chapter pages was run on 2026-10-25 from a fresh unzip of that chapter's kit, with Python 3.13.1. Each kit also passed `validate.py` and went red on `validate.py --bad`.

## How to use a chapter

The repository behind the case study is private. The kits are the way in. Whether the repository becomes public is the author's decision, and there is no promise or date. You do not need it.

1. Download the chapter's kit from the table below.
2. Compare its checksum with the one in the table.
3. Unzip it into an empty folder. The zip makes one folder, for example `ch02-hooks`. That folder is the kit root.
4. Run the commands on the chapter page from the kit root. The page shows each command and the output I got.
5. Run the `--bad` command. It must go red. A check that has never been seen failing is not yet evidence of anything.

Each kit holds the chapter spec, a chapter note (`CHAPTER.md`), the validation script, the code, the tests, the examples, the failing fixture and a `README.md`. The README and `CHAPTER.md` give the same commands as the page. Some links inside a kit's `CHAPTER.md` point to other chapters. They work only in the full repository.

**Python.** Every kit needs Python 3.9 or newer and uses only the standard library. The kit README says it was run from a fresh folder under Python 3.9.6, 3.12.8, 3.13.1 and 3.14.5. Versions 3.10 and 3.11 were not tested. The default `python3` on my machine is 3.13.1, so the outputs on these pages come from 3.13.1. Type `python3.12` instead of `python3` if you want that version. The commands use `python3 -I`. The `-I` flag keeps Python from reading your own files, so the result is the same on every machine.

**Systems.** The commands are for macOS and Linux. I did not test Windows.

**Time.** Each chapter page gives a time for running the steps. A step is one file read, one command run or one comparison. Minutes are the steps rounded up to the next 5. Steps marked optional are not counted. The count includes the checksum compare and the red run. Reading the code takes longer: about 20 to 30 minutes more for most chapters.

**The red run.** Every chapter ends with `python3 -I validate.py --bad`. It runs the checks on a copy that is built to fail, and it must exit with code 1. The last line is `validate: FAIL` with a count. Each chapter page shows the exact output and one sentence on what is special in that chapter. In some outputs a path such as `chapters/02-hooks/dispatch.py` appears. That is the layout of my own repository, not of the kit. Ignore the folder part.

## What the case study does not show

1. I ran nothing inside real Claude Code, Codex or Gemini. The case study is documentation only for those tools. The chapters test their own code. What the chapters say about those tools comes from their public documentation, with the fetch date on the setup pages.
2. The judge in chapter 4 and the parser in chapter 9 involve no language model. They are rule based stand-ins so that the tests repeat.
3. The section on models larger than memory in chapter 12 is descriptive. I ran no such model, and the spec gives no speed numbers.
4. The measured retrieval numbers in chapters 6 and 12 come from one small set of 44 memories and 34 queries, written by one person. They are weak evidence. The setup page on [relevance and re-ranking](../setup/relevance-and-reranking/) says what they do and do not show.
5. Chapter 8 is a design. The tests prove the file format and the chain check. They do not prove that personas help.
