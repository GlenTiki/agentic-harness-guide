**Status.** Built in the case study. Every command and output below was run on 2026-10-25 from a fresh unzip of `ch12-local-models.zip`, with Python 3.13.1. The one exception is the stored dense and hybrid outputs, which you read from a clone of the guide repository, not from the kit.

**Time.** Running the steps takes about 5 minutes (5 steps, [counted like this](../#how-to-use-a-chapter)). Reading the code takes longer: about 20 to 30 minutes more.

## The weak spot

Everything costs [tokens](../../glossary/#token) and sends data out. Small local models can do the small jobs.

## Goal

Run embedding and indexing locally and in the background, with every model optional and every test passing without them.

## What is in the kit

- `embed.py`, an embedding client with two embedders. One is a hashing stand-in that needs no model (the tests use it). The other is an Ollama embedder with checks on the reply.
- `dense_eval.py`, which scores BM25, dense retrieval and a hybrid (reciprocal rank fusion, k=60) on the evaluation set from chapter 6.
- `indexer.py`, a background job that builds the search index. It is resumable, takes a lock, has a time budget and can lower its own priority with `--nice`. It writes an index file and a status file.
- `validate.py`, which finds a stale index.

## Get the kit

Download [ch12-local-models.zip](/agentic-harness-guide/downloads/ch12-local-models.zip). Then run these commands in the folder that holds it:

```text
shasum -a 256 ch12-local-models.zip
unzip ch12-local-models.zip -d kit
cd kit/ch12-local-models
```

The hash must be `40f3e586970f77188ddab30a6020b712e5fe0c7394d970e17de7305fa83bd898`. If it differs, stop. On Linux use `sha256sum`. This folder is the kit root. Run every command from it. [How the kits work](../#how-to-use-a-chapter).

## Steps

1. Compare the checksum, then unzip (see above).
2. Run the evaluation with the hashing stand-in: `python3 -I dense_eval.py`.
3. Build the index for the example documents, then run the same command again. The second run embeds 0 files.
4. Run the validator: `python3 -I validate.py`. It prints `validate: PASS`.
5. Optional: install Ollama, run `ollama pull nomic-embed-text`, then `nice -n 10 python3 -I dense_eval.py --ollama`. Add `--nomic-prefixes` for the prefix variants.
6. Optional: run the live test with `RUN_LIVE_OLLAMA=1 python3 -I -m unittest discover -s tests -t . -k Live`.
7. Optional: build the index with the real model at low priority, with `--embedder ollama --nice 10`.
8. Prove the check can fail: `python3 -I validate.py --bad`. The exit code is 1.

### Measured results with a real model

These numbers come from a run of the optional steps on 2026-10-25. The stored outputs are in [examples/retrieval-eval/outputs](https://github.com/GlenTiki/agentic-harness-guide/tree/main/examples/retrieval-eval/outputs). The set is the one from [chapter 6](../ch06-rerank/): 44 memories and 34 queries that a person labelled. The model is `nomic-embed-text` (137M parameters, 768 dimensions, as `ollama show` reported), run through Ollama on one laptop. Two dense runs gave identical output.

| system | precision@3 | hit@3 | MRR |
| --- | --- | --- | --- |
| bm25 | 0.265 | 0.794 | 0.643 |
| dense, nomic-embed-text | 0.333 | 0.941 | 0.905 |
| hybrid, reciprocal rank fusion (k=60) | 0.275 | 0.824 | 0.795 |
| dense, with the model's search prefixes | 0.333 | 0.971 | 0.911 |
| hybrid, with the model's search prefixes | 0.275 | 0.824 | 0.808 |

For comparison, chapter 6 measured a cross-encoder on the same set: precision@3 0.275, hit@3 0.794 and MRR 0.803.

1. Dense retrieval found a correct memory in the top three for 32 of 34 queries. BM25 did so for 27.
2. The fusion with BM25 scored lower than dense alone. I did not investigate why.
3. The prefix variant is one query better on hit@3. That is within noise on 34 queries.
4. The set is small, written by one person and built to use other words than the memories. It does not show that dense retrieval is better in general. Measure on your own memories.

## What is not tested

The hashing embedder is for tests only. It scored below BM25 on this set, as expected, because it only matches shared words. Part 4 of the spec lists options for models larger than memory (llama.cpp memory mapping, the "LLM in a flash" paper, AirLLM). I ran none for this chapter. The section is descriptive, and the spec gives no speed numbers on purpose. The dense numbers come from one local model on one laptop and one small evaluation set.
