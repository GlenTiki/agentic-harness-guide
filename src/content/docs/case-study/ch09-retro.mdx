**Status.** Built in the case study. Every command and output below was run on 2026-10-25 from a fresh unzip of `ch09-retro.zip`, with Python 3.13.1.

**Time.** Running the steps takes about 10 minutes (9 steps, [counted like this](../#how-to-use-a-chapter)). Reading the code takes longer: about 20 to 30 minutes more.

## The weak spot

The same mistake twice. Feedback in chat disappears. Feedback in a vague note is never acted on.

## Goal

Turn rough feedback into the four-part form and a reviewable list of proposed fixes.

## What is in the kit

- The retro format: what went well first, then each problem as what it was, what happened and what I preferred.
- `retro.py` with a `parse` command, which sorts rough notes into the form and writes a proposals file, and a `check` command. `check --draft` allows open questions. A strict `check` does not.
- A rule-based parser. It reads the cues in the table below. A line with no cue stays in a Raw words block and becomes a question.
- A proposals file. Each proposal has a source issue, a status (proposed, accepted or rejected) and the check that would prove it works.

| Cue at the start of a line | Meaning |
| --- | --- |
| `+ `, `good:`, `went well:`, `liked:`, `win:` | something that went well |
| `- `, `bad:`, `problem:`, `issue:`, `went wrong:` | a new problem |
| `what it was:`, `it was:`, `was:` | field "What it was" |
| `what happened:`, `happened:` | field "What happened" |
| `what i preferred:`, `preferred:`, `i wanted`, `next time:` | field "What I preferred" |

Case does not matter.

## Get the kit

Download [ch09-retro.zip](/agentic-harness-guide/downloads/ch09-retro.zip). Then run these commands in the folder that holds it:

```text
shasum -a 256 ch09-retro.zip
unzip ch09-retro.zip -d kit
cd kit/ch09-retro
```

The hash must be `566f068ce30b19d7207890fb89c6f050b9d2c7747af4fdc16d976bc620d9efd4`. If it differs, stop. On Linux use `sha256sum`. This folder is the kit root. Run every command from it. [How the kits work](../#how-to-use-a-chapter).

## Steps

1. Compare the checksum, then unzip (see above).
2. Read `example/rough-notes.txt`. It is how a person writes after a long day.
3. Turn it into a draft with `retro.py parse`. The command writes `scratch/retro.md` and `scratch/proposals.md` and prints one open question.
4. Check the draft with `--draft`. It passes.
5. Check it strictly. It fails, because the question about issue 2 is open.
6. Answer the question in the file and run the strict check again. It passes.
7. Read `example/retro.md` and `example/proposals.md`. They are the finished version.
8. Run the validator: `python3 -I validate.py`. It prints `validate: PASS`.
9. Prove the check can fail: `python3 -I validate.py --bad`. The exit code is 1.

## What is not tested

The file `fixtures/bad/ramble.txt` holds three lines with no cue. The kit says the parser produces a draft with two questions, keeps every original word in the Raw words block and writes no proposals, and that the tests assert this. I did not run that file for this page. No language model is involved in this chapter. The parser is rule based. It does not understand meaning, so it cannot turn a real ramble into a good retro by itself. Its job is to be safe: it keeps the words, asks questions and invents nothing. In practice an [agent](../../glossary/#agent) that can reason would do the first pass, and these checks would be the gate. In my own setup there is no praise-first retro. This is a design built here.
