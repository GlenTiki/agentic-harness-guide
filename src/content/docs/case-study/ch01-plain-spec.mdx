## The weak spot

Vague requests. A spec that can be read two ways will be built one way, and it may not be yours.

## Goal

Have specs in simple English that a rule-based linter can check, and know exactly what that linter cannot check.

## What is in the kit

- `example/TEMPLATE.md` and a worked example, `example/notes-add.md`.
- `plainlint.py`, a linter with five rules: sentence length (25 words in a description, 20 in a numbered step), passive voice, a list of banned vague words, en/em dashes, and a readability grade (Flesch-Kincaid, limit 9).
- `validate.py`, which lints everything in `example/` and `SPEC.md`.
- Optional rules in the Vale format, in `vale/`. The tests do not need Vale.

## What you should see

`[exit code N]` is my addition, not program output. `<kit>` stands for the full path of the kit root.

The linter reads prose, not a test script. These excerpts show the actual inputs in `example/notes-add.md` and `fixtures/bad/vague.md`:

```text
Good spec:
1. The tool trims the spaces around the text.
2. The tool refuses the text if it is empty.
3. The tool refuses the text if it holds a new line or a tab.

Bad fixture:
The note adding feature is designed to robustly handle various kinds of input and other things, and it was built so that it can be easily extended by whoever happens to be maintaining the code in the future, etc.

1. The text is checked and then the tool is made to write the line to the file as needed.
```

`plainlint.py:lint_text` applies the following checks. This is simplified pseudocode; Markdown parsing, the word list and the grade formula are omitted.

```text
for each prose sentence:
    limit = 20 for a numbered step, otherwise 25
    report sentence-length when word_count > limit
    report passive-heuristic when the passive regex matches
    report vague-word for each banned word or phrase found
report dash for an en dash or em dash in a prose unit
report readability when the document's estimated grade > 9
```

The good spec should have no findings. The bad fixture should fail the length, passive, vague-word and readability checks. It contains no en dash or em dash, so these two sentences do not exercise the fifth rule. A repair would name the actor, replace vague terms with the intended behaviour, and split the long sentence; no rewritten-fixture run is recorded below.

## Steps

1. Compare the checksum, then unzip (see above).
2. Read `example/TEMPLATE.md` and the worked example `example/notes-add.md`.
3. Lint one file: `python3 -I plainlint.py example/notes-add.md`.
4. Run the validator: `python3 -I validate.py`. It prints `validate: PASS`.
5. Run the unit tests: `python3 -I -m unittest discover -s tests -t .`. The last line is `OK`.
6. Prove the check can fail: `python3 -I validate.py --bad`. The exit code is 1.

## What is not tested

The linter cannot check your words against the official Simplified Technical English dictionary. Open checkers, this one included, do not contain that dictionary. It is part of the ASD-STE100 standard, which ASD gives free to anyone who fills in its request form. The linter cannot check word sense or meaning. The passive-voice rule is a heuristic, and the test `test_known_false_positive_is_documented` records a sentence it flags wrongly. Vale is optional and the kit does not install it: `vale --config vale/.vale.ini example/notes-add.md`. The Vale rules mirror three of the rules (vague words, sentence length and passive voice) and do not compute the readability grade. I did not run Vale for this page. On 2026-10-24 I ran Vale 3.22.0 on the sample spec and on the failing fixture. The sample spec had 0 findings. The failing fixture had 5 errors and 5 warnings.
