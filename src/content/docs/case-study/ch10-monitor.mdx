*Audience: a reader who wants to build along. An agent must not run any command on this page unless the user asks for it in the current session.*

**Status.** Built in the case study. Every command and output below was run on 2026-10-25 from a fresh unzip of `ch10-monitor.zip`, with Python 3.13.1.

**Time.** Running the steps takes about 10 minutes (9 steps, [counted like this](../#how-to-use-a-chapter)). Reading the code takes longer: about 20 to 30 minutes more.

## The weak spot

Nobody sees the system think. A status page can show a green light that is days old.

## Goal

Record events as plain text and show a board that says where each value came from and when, and says Unknown when it cannot.

## What is in the kit

- An append-only JSON Lines event log. Each event has a source, a kind, a status, a detail and a time in UTC to the second, ending in `Z`.
- `monitor.py` with three commands: `record` appends an event, `board` builds a status board in Markdown or HTML, and `freshness` exits non-zero when something is stale.
- `example/board.json`, a config that lists the signals, their sources and how old an event may be. A signal with no event shows `UNKNOWN`.
- A fixed clock option, `--now`, so that a result does not change with the date.

## Get the kit

Download [ch10-monitor.zip](/agentic-harness-guide/downloads/ch10-monitor.zip). Then run these commands in the folder that holds it:

```text
shasum -a 256 ch10-monitor.zip
unzip ch10-monitor.zip -d kit
cd kit/ch10-monitor
```

The hash must be `25cdabbadc776da78de9823975468d3d12a68888d082833beffb46f277c84122`. If it differs, stop. On Linux use `sha256sum`. This folder is the kit root. Run every command from it. [How the kits work](../#how-to-use-a-chapter).

## What you should see

`[exit code N]` is my addition, not program output. `<kit>` stands for the full path of the kit root.

The board and freshness runs use the same event-to-state function. `example/events.jsonl` records a successful hook at `2026-10-24T09:10:00Z`; `example/board.json` gives that hook a maximum age of 3600 seconds. No backup event exists, and the backup signal has `required: false`.

This is simplified pseudocode for `monitor.py:build_rows` and `red_reasons`. JSON validation, timestamp parsing and rendering are omitted:

```text
for each configured signal:
    find events with the same source and kind
    if none: state = unknown
    otherwise select the event with the latest timestamp
    age = now - event.time
    if age < 0: state = unknown
    else if event.status == fail: state = fail
    else if age > signal.max_age_seconds: state = stale
    else: state = ok
freshness fails for each required signal whose state is not ok
also fail if the newest log event exceeds --max-log-age
```

At the fixed clock `2026-10-24T09:30:00Z`, the hook event is 1200 seconds old, so expect OK. The missing optional backup shows UNKNOWN without failing freshness. Moving the clock past the hook's age limit makes its old success stale. A recorded failure stays FAIL even when old; staleness does not hide it.

The bad log contains only these two events; this display selects fields from `fixtures/bad/events.jsonl` and omits `detail`:

```text
time                  source    kind   status
2026-10-01T08:00:00Z  check.sh  check  ok
2026-10-24T09:10:00Z  dispatch  hook   fail
```

At the validator's fixed clock, expect `Checks pass` to be STALE, `Hooks ran` to be FAIL, and required `Memory recall` to be UNKNOWN because there is no recall event. These are three different reasons to refuse a green verdict. Recording fresh successful events after the corresponding work succeeds can change those states; merely rebuilding the board cannot.

## Steps

1. Compare the checksum, then unzip (see above).
2. Read `example/events.jsonl` and `example/board.json`.
3. Build the board for a fixed time. The `Backup` row shows `UNKNOWN`.
4. Run `mkdir -p scratch`, then build an HTML page and open it: add `--out scratch/board.html` to the board command.
5. Run the freshness check at the fixed time. It prints `freshness: GREEN`.
6. Run it without `--now`. The example events are old by now, so it prints `RED` lines and exits with code 1.
7. Record an event: `python3 -I monitor.py record --log scratch/e.jsonl check.sh check ok "ALL CHECKS PASSED"`. It prints nothing and adds one line to the log.
8. Run the validator: `python3 -I validate.py`. It prints `validate: PASS`. The validator fixes the clock at 2026-10-24T09:30:00Z.
9. Prove the check can fail: `python3 -I validate.py --bad`. The exit code is 1.

## What is not tested

The board is a snapshot built when you run the tool. It is not a live dashboard. The log proves that something wrote a line. It does not prove that the line is true. A part that crashes before it logs leaves no new line. With no earlier event, the board shows unknown. With a recent OK event, it stays green until that event exceeds `max_age_seconds`; only then does it show stale. That delay is a blind window, and you see the change only when you rebuild the snapshot. Nothing here is connected to a real assistant's hooks. To wire it in, add a call to `monitor.py record` at the end of a hook from chapter 2 or at the end of `check.sh`.
