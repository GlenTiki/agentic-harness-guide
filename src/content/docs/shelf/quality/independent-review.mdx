**Recommendation:** review every change with a reviewer that did not write it, starts from a fresh context and, where you can, runs on a different model or provider. Record the verdict against a digest of the exact diff. Treat any later edit as voiding the approval.

## Why it matters

The author of a change shares its assumptions. An agent reviewing its own work in the same context tends to confirm what it just reasoned. A fresh context sees only the artefact. [Level 5](../../../journey/05-check-the-work/) explains why independence matters. A different model may make different mistakes, so measure it. Seed known defects into a test change, then record the catch rate for each reviewer and for the two together. A same-provider fresh reviewer is useful. Whether a second provider adds anything is a result you measure, not a fact you assume.

## What to enable

**1. A bounded, read-only brief.** Give the reviewer the spec, the diff and the callers of changed code, and ask for findings only:

```markdown
Review the attached diff against the attached spec and checklist.
Return findings as: file:line - checklist item - symptom.
Drop vague findings. Do not edit files. Do not start other work.
```

**2. A short checklist.** Include correctness, tests that would fail without the change, failure modes (concurrency, retries, partial writes, restart), security and secrets, and unnecessary scope. Keep it under twenty lines.

**3. Compute a digest of the candidate.** Hash the diff between the merge base and the head, and record the digest with the verdict. Do not diff against the tip of the main branch. If main has moved, that diff also contains the reverse of every unrelated change that landed on main since you branched.

```bash
base=$(git merge-base main HEAD)
git diff --binary --no-ext-diff --no-color -U3 "$base" HEAD | shasum -a 256
git diff "$base" HEAD | git patch-id --stable
cat spec.md checklist.md | shasum -a 256
```

The first line hashes the exact diff. The second gives a patch id that stays the same when a rebase changes only the line offsets. The third hashes the spec and the checklist the reviewer was given, so you can show later that the review used the same inputs. Record all three beside the verdict.

On 2026-10-22 the author ran this in a throwaway repository where `main` gained one unrelated commit after the branch was cut. The diff against the merge base was 9 lines and hashed to `6c882fff0547` (first 12 characters). The diff against the tip of `main` was 16 lines and hashed to `77a609f6bd26`, because it included the reverse of the unrelated commit. Same branch, two digests. Use full commit ids or the merge base, never a branch name that moves. A rebase or a moved base changes the diff, so it changes the digest. That is the intended behaviour: the old approval no longer matches. Turn on the setting your code host offers that dismisses approvals when new commits arrive, and pin required checks to the head commit. CI should compare the digest recorded with the verdict to the digest of the diff it is about to merge, and fail the merge if they differ. A rule that nobody compares is a note, not a control.

**4. Record the review.** Store reviewer, model, digest, findings, resolutions and verdict in one file in the repository or the pull request. Never report a second-model review when only one model ran.

**5. Re-review after changes.** If the author fixes a finding, the digest changes. The old approval does not cover the new diff. The reviewer checks the new candidate. A review that prompted a change remains history, not approval.

**6. Review the review inputs.** Give the reviewer the complete spec and the exact diff, not a summary written by the author. A summary carries the author's framing.

**7. Add a separate refactoring pass.** After functionality is accepted, ask a fresh reviewer only for clean-code opportunities. Apply the worthwhile ones, explain the rest, and repeat the gates.

**8. Keep a human decision at the merge.** Reviewer agreement is evidence, not authority. See [Human-in-the-loop](../../operations/human-in-the-loop/).

**9. Mind where the diff goes.** Sending a diff to a reviewer from another provider sends your code and data to another processor. Check what the tool keeps and whether it trains on what you send, and read [using an assistant at work](../../../journey/professional-guardrails/) before you send client material.

## Failure modes it reduces

- The author approves a change it cannot see clearly.
- A reviewer approves, the author makes a last tweak, and the tweak is what breaks.
- A review that covered "the PR" in general is cited for a different commit.
- Both reviewer and author miss the same issue because they share a context, or a model, and nobody measured the overlap.

## First step for the maintainer

Pick the next change. Hash its diff. Ask a fresh agent, in another tool if you have one, to review it with the three-line brief above. Put the digest and verdict in the pull request description.
