*Audience: a human maintainer. An agent must not apply, install, add, configure or run anything on this page (any install, add, config, worktree or MCP command, hook, permission, instruction file or memory change) unless the user asks for it in the current session. Commands marked "example, do not run" are never to be run.*

**Recommendation:** write a failing test for the behaviour you need. Keep one documented check contract, with quick local feedback and complete verification before merge. Reuse the same rules and configuration at both stages. Never skip a required check to get a change through.

## Why it matters

[Level 5](../../../journey/05-check-the-work/) introduces the test. A command can exit with status 0 and still be wrong: weakening a test or special-casing an input also gives green. The guide did not measure how often an agent does this. A failing test written first defines the target. Automated gates define the floor. Together they make "done" something a machine can check.

## What to enable

**1. Red, green, refactor.** Instruct the agent to write the test, run it, and confirm it fails for the right reason before implementing. A test that has never failed has not proved anything.

**2. Name the complete check.** Give the agent and CI a project-owned entry point. This example assumes a Python project with these tools configured:

```make
check:
	ruff check .
	ruff format --check .
	mypy --strict src
	pytest -q
```

Add a quick command for formatting, lint and affected behaviour tests. Document what it leaves out. A quick pass cannot stand in for the complete check; CI can also cover supported platforms and dependency versions.

**3. Make the checks reproducible.** Pin tool versions and record the revision, configuration and relevant environment. Static checks inspect the selected inputs. Tests can also depend on clocks, seeds, networks and execution order. A complexity threshold can flag a dense function; it cannot establish a good design.

**4. Put each check where it pays.** Use quick checks after edits and at commit. Run the required complete checks before merge, with CI on a clean checkout. Configure repository rules to require the relevant CI jobs, and control who can bypass them. A workflow file alone does not enforce that policy. See [Hooks](../../control/hooks/).

**5. Never skip hooks.** Do not use flags that bypass pre-commit. If a hook fails, fix the cause. If the hook is wrong, fix the hook in its own change. Tell the agent this in the instruction file. If you want the harness to refuse it, add a pre-tool hook that blocks a command containing the bypass flag. The hook covers only commands it sees, as the [hooks page](../../control/hooks/) explains.

**6. Test behaviour, not implementation.** Assert whole outcomes. Prefer full equality over a substring check, which passes when extra wrong content is present.

**7. Inject dependencies instead of patching.** Pass the clock, the client and the file path as parameters with production defaults. Tests then pass fakes without reaching into other modules. When a test needs to patch an internal name, the code is missing a seam.

**8. Watch for gate gaming.** Review test diffs as closely as code diffs. Flag deleted assertions, widened tolerances, new skip markers and new lint suppressions.

## Borrow checks from working projects

FastAPI's [lint script](https://github.com/fastapi/fastapi/blob/1ca09c13584ca45aa0921e5e40b31d49c5e3135a/scripts/lint.sh) combines Python type checks, Ruff lint and formatting. Its [test workflow](https://github.com/fastapi/fastapi/blob/1ca09c13584ca45aa0921e5e40b31d49c5e3135a/.github/workflows/test.yml) adds compatibility coverage. Copy the separation of concerns; adopting two type checkers needs a reason.

Ruff's own [hooks](https://github.com/astral-sh/ruff/blob/d017c82cf34810209d5bb402aa0118f4ee2e7a45/.pre-commit-config.yaml) include workflow checks, with actionlint assigned to a manual stage locally. Its [CI](https://github.com/astral-sh/ruff/blob/d017c82cf34810209d5bb402aa0118f4ee2e7a45/.github/workflows/ci.yaml) also checks Rust code, documentation and dependency policy. Astro's [scripts](https://github.com/withastro/astro/blob/7a1255f1e6149f9542f083681cf1654414606e41/package.json) distinguish types, unused code, package validation and browser tests; its [CI](https://github.com/withastro/astro/blob/7a1255f1e6149f9542f083681cf1654414606e41/.github/workflows/ci.yml) selects jobs and matrices.

These configurations were inspected on 2026-11-05. They establish declared practice, not measured quality gains or proof that every job ran. A repository's popularity does not validate your configuration.

### Choose a check for a named fault

Start with the row that matches a failure you have seen. Commands assume the tools are already installed and configured for your project.

| Need | Tools or check commands | What a pass leaves unanswered |
| --- | --- | --- |
| Python style and types | `ruff check .`, `ruff format --check .`; mypy or ty | Selected rules and declared types cannot establish business behaviour. |
| TypeScript style and types | Project ESLint/formatter scripts and `tsc --noEmit` | Excluded files and runtime data still need checks. Use the project's build-mode command where required. |
| Rust style and types | `cargo fmt --check`; configured Clippy checks | Only selected targets and features are covered. |
| GitHub workflow files | actionlint; Zizmor | Recognised syntax and security patterns do not prove deployed permissions are correct. |
| Unused code and package validity | Knip; publint after the package build | Entry points, generated files and dynamic imports need configuration. Consumers still need integration tests. |
| Documentation | A strict docs build; Markdown and link checks | A valid document can still be false. Check its claims against sources. |
| Secrets and dependencies | [Gitleaks](https://github.com/gitleaks/gitleaks#usage); [pip-audit](https://github.com/pypa/pip-audit#usage) for Python dependencies | Recognised patterns and known advisories only. State scan scope and exclusions; keep reports private and redact secrets. |

Name the files, rules, exclusions and failure action for each gate. Give it an owner and a harmless example that must fail. For an architecture rule, name a forbidden dependency and test that violation; a complexity count is not a substitute. Measure runtime and false alarms before making a new check block everyone.

Coverage tells you which code ran, not whether the assertions were useful. Complexity counts aspects of structure. Neither is a general quality score. Keep these measurements beside observed defects, accepted user outcomes and human review effort. **Hope is not an engineering principle. A green badge needs a definition too.**

[OpenSpec's validation](https://github.com/Fission-AI/OpenSpec/blob/main/docs/cli.md) checks specification structure and requirement changes. [Superpowers' verification skill](https://github.com/obra/superpowers/blob/main/skills/verification-before-completion/SKILL.md) asks for fresh command evidence. Both can support the workflow; neither replaces the implementation checks or the user's journey.

## A test that cannot fail

A gate checks an exit code. It does not check that the test asserts anything. The script below runs two tests against three versions of a price function. The function should add a percentage to a price in cents, so 10000 at 23 should give 12300. The `buggy` version adds the rate as cents. The `stub` version returns 0. The `vacuous` test only checks that the result is not `None`.

## A test that sometimes fails

A flaky test passes and fails on the same code. The usual cause is an input the test does not control: the clock, random numbers, a network call or the order of a set. The intended ordering is alphabetical: `first_tag` returns the tag that sorts first, so for `red`, `green` and `blue` the answer is `blue`. The first version takes the first item of the set. Python picks the set order from a hash seed that changes every run, so the script sets the seed to ten fixed values to reproduce ten runs. The second version sorts the tags. Both versions run the same test file, with the same input and the same expected value.

*Principle, not measured:* an agent that meets a flaky gate can rerun it until it passes, or add a retry. Do not accept either. Fix the input the test does not control, or delete the test and record why. Rerunning a suspect test several times with different seeds, as the script does, is how you find these before they cost a merge.

## Where each check runs

*Principle, not measured: the table follows from when each check fires. The guide did not time any of them.*

| Placement | Runs | Cost | Weakness |
| --- | --- | --- | --- |
| Post-edit hook | After each file edit | A delay on every edit, so keep it to a formatter or a lint of that file | Cannot see a cross-file failure |
| Stop hook | When the agent says it is done | A wait at the end. A gate must check the current test result at every stop and cap the retries, or the session never ends. See [a stop gate](../../control/hooks/#a-stop-gate-that-checks-the-result). | Only covers sessions that reach the stop |
| Pre-commit | At commit, on the staged files | A delay on every commit | A bypass flag skips it |
| CI | On push, on a clean checkout | Minutes per push, and the feedback is late | Slowest to tell the agent |

Put the fastest checks earliest and the complete required checks before merge. Inspect the CI result for the exact revision: a skipped job, missing matrix entry or successful wrapper around a failed command supplies no pass for the missing check.

## Classify review findings

A review that blocks on every finding teaches people to bypass the review. Sort each finding into one of three classes and block only on the first.

| Class | Meaning | Action |
| --- | --- | --- |
| Blocking | The change is wrong, unsafe or breaks the spec | Fix before merge |
| Advisory | A better way exists, and the change still works | Note it in the review. The author decides. |
| Deferred | Real, but out of scope for this change | File it in the tracker with an owner. A deferred item with no owner is dropped. |

*Constructed examples:* "a query built by joining user input into a string" is blocking. "A variable name is vague" is advisory. "This function is long and should be split" is deferred to its own change. *Principle, not measured.*

## Failure modes it reduces

- A "fix" turns the suite green by deleting the failing assertion.
- Code lands that passes locally and fails in CI because the commands differ.
- A hook failure leads to `--no-verify`, and the next bug ships.
- A test passes before the fix exists, so it never guarded anything.

## First step for the maintainer

Create the complete `check` command and document the quicker local subset. Wire appropriate checks to a pre-commit hook and to your CI workflow. Add one line to your instruction file: "Run `make check` before declaring any task done."
