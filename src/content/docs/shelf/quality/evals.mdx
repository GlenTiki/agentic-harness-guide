**Recommendation:** give every step where a model makes a decision its own eval. Build the fixtures from real model output. Before you trust a check, make it fail on purpose. Score new runs against the old rubric.

## Why it matters

Unit tests cover code that returns the same answer each time. A model step varies from run to run, so a single passing run proves little. A step with no eval is a step you cannot change safely, because you cannot tell whether a change helped.

## What to enable

**1. One eval per decision point.** List every place a model chooses something: a router picks a tool, a classifier picks a label, a reviewer picks a verdict, a parser reads model text. Give each a small set of cases with expected outcomes. A stub that returns a canned answer tests your wiring and not the model, so do not count it as an eval.

**2. Use real output as fixtures.** If your code parses model output, capture actual replies and test against those. Hand-written examples are tidier than real replies and hide the quirks that break parsers, such as extra prose, code fences and missing fields.

**3. Repeat runs.** Run each case several times. Report the pass count out of the total. Three runs cannot establish reliability either way. If a step passes all n runs, the failure rate is only bounded near 3 in n (the rule of three), so three clean runs leave a bound near 100 percent. Three runs are weak evidence. A step that works 95 percent of the time passes all three runs about 86 percent of the time (0.95 x 0.95 x 0.95). A step that works 67 percent of the time still passes all three about 30 percent of the time. One clean result in three tells you little about which step you have. For small samples, use a binomial confidence interval and state it. A single run would show none of this.

**4. Prove the check can go red.** Before you rely on a green result, change the input or the code so that it must fail, and confirm it does. A grader with a typo in its pattern reports "no failures" for everything. Include a known-positive control in each run.

**5. Hold the rubric still.** When you change a prompt or a model, score the new output with the old rubric and the old cases. If you change the rubric at the same time, you cannot attribute the difference. Change one thing, then re-baseline deliberately.

**6. Keep graders deterministic where you can.** Prefer an executable check, such as "does this output parse" or "does this command exit 0", over another model's opinion. When you must use a model as a grader, give it a narrow question and spot-check its grades by hand.

**7. Pin and record the model.** A silent model change moves your baseline. Pin the model version where your provider allows it. Record the model name, the version and the date with every run. Re-run the cases when the provider announces a change, and when the scores move without a change of yours.

**8. Record the baseline.** Store the cases, the raw outputs and the scores. A later run can then be compared and replayed without calling the model again.

**9. Pilot before scale.** On a long run, try five samples first. Dump the parsed output. Confirm that nothing is filtered by a hard-coded list and no placeholder is unresolved. Then run everything. Before you send real inputs to a hosted model or a model grader, read [using an assistant at work](../../../journey/professional-guardrails/) for what may leave your organisation.

## Calibrate a model judge against human labels

When a model grades another model's output, treat the judge as a measuring instrument and calibrate it. Label a set of outputs by hand as pass or fail. Run the judge on the same outputs. Then compare.

Raw agreement is the share of cases where the two labels match. It flatters a judge when one label is common. A judge that passes everything agrees with the human on every output the human passed. The fix is a chance-corrected statistic, Cohen's kappa: the agreement beyond what you would expect if each rater labelled at random with their own pass rate. It is 1 for perfect agreement and 0 for chance level.

Also count the failures the judge caught, because a judge is there to catch failures. Write the pass criterion before you look at the numbers. The two values below are starting points to set for your own stakes, not standards.

When the judge fails the criterion, read the disagreements. Narrow its question and add one example per kind of miss. Do not edit the labels to suit the judge.

Split the labelled outputs into two sets before you start. The development set is the one you read, tune against and re-run as often as you like. The acceptance set is labelled once, kept unread by whoever tunes the judge, and scored once per candidate judge. Every change you make in response to development-set misses fits the judge to that set, so its score stops being an estimate of how the judge behaves on new outputs. Apply the criterion to the acceptance set only. Keep the development cases as a regression check, since a fix for one miss should not break a case that passed. If you score the acceptance set repeatedly and adjust after each score, it has become a second development set: label a new one. The 20 cases above are a development set; the example does not give an acceptance score.

## Regression suite for a prompt change

A regression suite answers one question: did this change make anything worse? It needs four things fixed before the change.

1. **Cases.** A set of inputs with known good outcomes, drawn from real input, kept in the repository.
2. **A criterion.** The pass rule written before the run. For example, every case passes at least 9 times in 10 runs, and no case that passed before now fails in more than 2.
3. **A pinned model.** The model version recorded in the suite, so a score moving means the prompt moved it. Re-baseline on purpose when you change the model.
4. **The old numbers.** Store the previous run so you can compare the two sets of counts, not recall them.

```text
suite: invoice-routing
model: <the exact model id you pin>
runs_per_case: 10
cases: cases/*.json
pass: every case at least 9 of 10; no case worse than its stored baseline by more than 2
```

That block is an illustration of the fields to keep, not a file format any tool reads.

## Reading a difference in few runs

The rule of three bounds what a clean run proves. The opposite case is just as common: a prompt change moves a step from 3 failures in 20 runs to 2. That is one fewer failure. Is the new prompt better?

Compute it before you claim it. Two exact calculations need no statistics library. The first asks how often a step whose rate had not changed would show 2 or fewer failures in 20 runs. The second, Fisher's exact test, compares the two sets of counts directly.

A step that did not change would show 2 or fewer failures about 4 times in 10 (0.405). One fewer failure is no evidence. Even 0 failures in 20 gives 0.115 against the old counts, so it is suggestive and not settled. The first calculation treats the old rate as known, which is generous to the new prompt.

## Failure modes it reduces

- A prompt change quietly lowers quality and nobody notices.
- A parser works on tidy fixtures and fails on real replies.
- A green dashboard hides a grader that never fails.
- A before/after comparison is meaningless because the rubric moved.
- A judge that agrees 80 percent of the time and still misses a quarter of the failures.
- A prompt change that is called an improvement on one fewer failure in 20 runs.

## First step for the maintainer

Choose the one model-driven step you worry about most. Collect ten real inputs, write the expected outcome for each, and run them three times. That table is your first baseline.
