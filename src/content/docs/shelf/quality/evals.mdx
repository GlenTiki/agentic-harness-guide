## Why it matters

Unit tests check specified code behaviour. A model step can vary from run to run, so a single passing run proves little. Without a relevant measure, you cannot tell whether a change helped.

## Start with the outcome

Known requirements can be checked before implementation: a total must reconcile, a required field must exist, a forbidden action must be refused. Uncertain model behaviour needs observation. Inspect actual failures before inventing a complex grader for them. This follows [Hamel Husain and Shreya Shankar's evals guidance](https://hamel.dev/blog/posts/evals-faq/), including their distinction between speculative evaluators and known constraints. Article fetched on 2026-11-04.

For a multi-step agent, first ask whether the user's complete task succeeded. Use step-level checks to diagnose where failures arise. Green individual steps do not establish a useful final result. Automate checks whose value justifies their construction and maintenance.

[Promptfoo](https://www.promptfoo.dev/docs/intro/) is one open-source option for comparing prompts and models across cases, with assertions and a results matrix. You still define the cases, acceptance rules and permitted data destinations. Running the tool locally does not stop its configured model providers receiving requests. ## Test the setup people actually use

A component check can pass while the assistant chooses the wrong tool or supplies the wrong arguments. OpenAI's [plugin-evaluation example](https://developers.openai.com/cookbook/examples/partners/harness_aware_plugin_evals/harness_aware_plugin_evals) compares shared cases across direct tools, a standalone loop and Codex. Differences in supplied instructions mattered. That is a configuration diagnosis, not a ranking of assistants.

Proposed exercise: use a known answer, missing data and an ambiguous request in one read-only workflow. Run the same cases through its component check and the assistant surface you use. Save the model, loaded instructions, available tools, actual calls and final answer. Check both the outcome and permitted actions. Fix one demonstrated difference, then repeat, including fresh cases. Keep failed runs in the denominator.

Preserve earlier candidates when a model judge guides revisions. Anthropic's [design-harness account](https://www.anthropic.com/research/harness-design-long-running-apps) notes that an intermediate design could be preferable to the final one. Compare candidates without their scores visible, against the original task and audience. Accessibility and working controls need their own checks. ## What to enable

**1. Map the decisions that affect the outcome.** List where a model chooses a tool, label or review verdict. Use observed failures and consequences to choose which need their own cases with expected outcomes. A stub that returns a canned answer tests your wiring and not the model, so do not count it as an eval.

**2. Use real output as fixtures.** If your code parses model output, capture actual replies and test against those. Hand-written examples are tidier than real replies and hide the quirks that break parsers, such as extra prose, code fences and missing fields.

**3. Repeat runs.** Run each case several times and report the pass count out of the total. Three runs cannot establish reliability: a step that works 95% of the time passes all three about 86% of the time. Even a 67%-reliable step passes all three about 30% of the time. [Choose enough trials](#earn-confidence-with-enough-trials) for the claim you need to make.

**4. Prove the check can go red.** Before you rely on a green result, change the input or the code so that it must fail, and confirm it does. A grader with a typo in its pattern reports "no failures" for everything. Include a known-positive control in each run.

**5. Hold the rubric still.** When you change a prompt or a model, score the new output with the old rubric and the old cases. If you change the rubric at the same time, you cannot attribute the difference. Change one thing, then re-baseline deliberately.

**6. Keep graders deterministic where you can.** Prefer an executable check, such as "does this output parse" or "does this command exit 0", over another model's opinion. When you must use a model as a grader, give it a narrow question and spot-check its grades by hand.

**7. Pin and record the model.** A silent model change moves your baseline. Pin the model version where your provider allows it. Record the model name, the version and the date with every run. Re-run the cases when the provider announces a change, and when the scores move without a change of yours.

**8. Record the baseline.** Store the cases, the raw outputs and the scores. A later run can then be compared and replayed without calling the model again.

**9. Pilot before scale.** On a long run, try five samples first. Dump the parsed output. Confirm that nothing is filtered by a hard-coded list and no placeholder is unresolved. Then run everything. Before you send real inputs to a hosted model or a model grader, read [using an assistant at work](../../../journey/professional-guardrails/) for what may leave your organisation.

## Earn confidence with enough trials

One good run is a demo. A larger, representative sample tells you more about whether the result will hold next time. It can expose rare failures and narrow uncertainty. It cannot fix biased examples, a broken grader or a workflow you keep changing during the test.

For a simple illustration, freeze the workflow and choose the sample size before you start. Test independent jobs drawn from the work you intend it to do. If every job passes, the exact one-sided 95% lower confidence bound on reliability is `0.05^(1/n)`, where `n` is the number of trials. This follows from setting the probability of an all-pass sample, `p^n`, to `0.05`; see [binomial confidence bounds](https://www.itl.nist.gov/div898/handbook/prc/section2/prc241.htm).

| Trials, with zero failures | One-sided 95% lower reliability bound |
| --- | --- |
| 30 | 90.50% |
| 300 | 99.01% |
| 3,000 | 99.90% |

Thirty clean runs still leave considerable uncertainty. Three hundred clean runs support a much stronger claim, under those assumptions. The familiar “rule of three” approximates the upper failure bound as `3/n`. Neither calculation promises that the next job will pass, or covers a different input population.

To establish good behaviour, define “good” and the required reliability first. For example, choose a 99% target and a fixed 300-trial test. Zero failures would put the lower bound above that target. If failures occur, calculate a bound from the actual counts; do not discard them or restart the count until you get a clean streak.

To claim an improvement, compare the old and new workflows on fresh cases with a planned statistical test. Choose the sample size for the improvement you need to detect. Statistical significance is evidence against a specified no-improvement hypothesis, not a certificate that the workflow is useful or safe. A tiny improvement can be statistically significant and still miss your reliability target. The [worked comparison below](#reading-a-difference-in-few-runs) shows why one fewer failure in a small sample proves little.

Keep development examples separate from the final evaluation. Repeated runs of one easy prompt can measure variability for that prompt, but cannot stand in for different real jobs. Report the numerator, denominator, confidence bound and conditions together. More samples buy better evidence. The gates and repairs must earn the better behaviour.

## Calibrate a model judge against human labels

When a model grades another model's output, treat the judge as a measuring instrument and calibrate it. Label a set of outputs by hand as pass or fail. Run the judge on the same outputs. Then compare.

Raw agreement is the share of cases where the two labels match. It flatters a judge when one label is common. A judge that passes everything agrees with the human on every output the human passed. The fix is a chance-corrected statistic, Cohen's kappa: the agreement beyond what you would expect if each rater labelled at random with their own pass rate. It is 1 for perfect agreement and 0 for chance level.

Also count the failures the judge caught, because a judge is there to catch failures. Write the pass criterion before you look at the numbers. The two values below are starting points to set for your own stakes, not standards.

When the judge fails the criterion, read the disagreements. Narrow its question and add one example per kind of miss. Do not edit the labels to suit the judge.

Split the labelled outputs into two sets before you start. The development set is the one you read, tune against and re-run as often as you like. The acceptance set is labelled once, kept unread by whoever tunes the judge, and scored once per candidate judge. Every change you make in response to development-set misses fits the judge to that set, so its score stops being an estimate of how the judge behaves on new outputs. Apply the criterion to the acceptance set only. Keep the development cases as a regression check, since a fix for one miss should not break a case that passed. If you score the acceptance set repeatedly and adjust after each score, it has become a second development set: label a new one. The 20 cases above are a development set; the example does not give an acceptance score.

## Regression suite for a prompt change

A regression suite answers one question: did this change make anything worse? It needs four things fixed before the change.

1. **Cases.** A set of inputs with known good outcomes, drawn from real input, kept in the repository.
2. **A criterion.** The pass rule written before the run. For example, every case passes at least 9 times in 10 runs, and the record lists every case that now passes fewer runs than its stored baseline, even when it still clears 9.
3. **A pinned model.** The model version recorded in the suite, so a score moving means the prompt moved it. Re-baseline on purpose when you change the model.
4. **The old numbers.** Store the previous run so you can compare the two sets of counts, not recall them.

```text
suite: invoice-routing
model: <the exact model id you pin>
runs_per_case: 10
cases: cases/*.json
pass: every case at least 9 of 10
report: every case below its stored baseline
```

That block is an illustration of the fields to keep, not a file format any tool reads.

## Reading a difference in few runs

The rule of three bounds what a clean run proves. The opposite case is just as common: a prompt change moves a step from 3 failures in 20 runs to 2. That is one fewer failure. Is the new prompt better?

Compute it before you claim it. Two exact calculations need no statistics library. The first asks how often a step whose rate had not changed would show 2 or fewer failures in 20 runs. The second, Fisher's exact test, compares the two sets of counts directly.

## Failure modes it reduces

- A prompt change lowers quality and nobody notices.
- A parser works on tidy fixtures and fails on real replies.
- A green dashboard hides a grader that never fails.
- A before/after comparison is meaningless because the rubric moved.
- A judge that agrees 80 percent of the time and still misses a quarter of the failures.
- A prompt change that is called an improvement on one fewer failure in 20 runs.

## First step for the maintainer

Choose the one workflow whose outcome you worry about most. Collect ten real inputs, write the expected outcome for each, and run them three times. That table is your first baseline.
