**Recommendation:** when the right note does not reach the assistant, first decide which of two things failed: the search never returned it (retrieved wrong), or it returned it too low (ranked wrong). The fixes differ. Then add a similarity floor, store the embedder name with the index, and measure each change on your own queries.

No tool-specific setting is named on this page. The scores come from the retrieval kit in [case-study chapter 6](../../../case-study/ch06-rerank/): 44 notes and 34 queries that one person labelled. The dense (embedding) rows are stored outputs from an earlier run, because no embedding model was installed for the offline runs here.

## Why it matters

Memory and search results are text that goes into the context ([context management](../context-management/), [memory](../memory/)). Principle, not measured: the scripts here measure retrieval, not what an assistant does with the results. When the wrong notes go in, the assistant may answer from them without any sign that they were the wrong ones. When the right note stays out, nothing signals the gap. A reply that ignores a rule you wrote can come from a retrieval failure and not from a failure to follow the rule. Check retrieval before you rewrite the rule. This guide does not measure how often each cause occurs.

## What to enable

**1. Classify each miss.** Take the queries where the right note did not reach the top k. Look at where it sat in a longer list, the candidate pool. Three outcomes:

| Outcome | Meaning | Where to fix |
| --- | --- | --- |
| ok | A correct note is in the top k | Nothing |
| ranked wrong | A correct note is in the pool but below the top k | The order: fusion, a re-ranker, weights |
| retrieved wrong | A correct note is not in the pool | The retrieval: a second retriever, the indexed text, the embedder |

A re-ranker cannot help a retrieved-wrong miss, because it only reorders what the pool holds. This is why you classify before you buy one. The count below uses BM25 with a pool of 10 and k = 3.

**2. Know which retriever suits which query.** A keyword search matches the words in the query. It finds an exact identifier, such as a code, a name or a standard number, because that token appears in few notes. An embedding search matches meaning. It finds a paraphrase that shares no word with the note.

**3. Fuse two lists with care.** Reciprocal rank fusion (RRF) gives a note `1 / (k + rank)` in each list and adds the scores. It rewards agreement between the lists. Use k = 60, as the kit does, and give both lists equal weight, unless you measure otherwise. The example fuses the live BM25 list with the stored dense top three.

**4. Add a similarity floor, and tune it.** Without a floor, the search returns the best of a bad lot, and an off-topic question still gets notes. A floor drops results whose similarity is too low. Every value is a starting value to tune on your own data, because the right value depends on the scorer and the notes. Sweep it with a set of off-topic queries as well as your normal ones, and count both kinds of error. The sweep below uses a bounded lexical similarity (tf-idf cosine, 0 to 1), because no embedding model was installed here. An embedder's cosine has another scale, so repeat the sweep with yours.

**5. Store the embedder with the index, and refuse a mismatch.** Vectors from two embedders cannot be compared, even when they have the same length. Vectors of different lengths cannot be compared at all, and some code compares them without an error. Write the embedder name and the vector length into the index file. On load, compare both with the embedder you are about to use, and raise an error if either differs. `examples/retrieval-diagnosis/vector_index.py` does this in about 30 lines and has tests for a wrong name, a wrong length, a damaged vector and a missing field.

**6. Measure each change.** Score the search before and after every change on the same labelled queries, as [the relevance page](../../../setup/relevance-and-reranking/) does. [Case-study chapter 6](../../../case-study/ch06-rerank/) gives you the kit. Add your off-topic queries to the set.

## Failure modes it reduces

- A re-ranker is added to fix a miss that the search never returned.
- An off-topic question receives notes and the assistant uses them.
- A fused list ranks a half-match above the right note.
- A new embedder is installed and the old index is queried with it, with no error.

## First step for the maintainer

Take the last five times the assistant ignored a rule you had written down. For each, find out whether the note was returned, and where it ranked. Write down which of the two failures it was.
