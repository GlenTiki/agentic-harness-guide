**Recommendation:** write the ask as goal, constraints, output shape and check, in that order. Make the check a required field of the output shape. Accept a reply only when a script has parsed it and re-computed what it can. Keep a fixed set of cases and re-run it whenever the prompt or the model changes.

No tool-specific setting is named on this page. The ideas work in any chat tool or harness that lets you read the reply as text.

## Why it matters

A good ask still gets a wrong reply some of the time. [Level 1](../../../journey/01-say-it-properly/) shows the parts of a good ask. This page turns those parts into something a script can enforce. A reply that a script can reject is a reply you do not have to read for form, so your attention goes to the content.

## What to enable

**1. Fix the order of the ask.** Put the parts in one order every time: goal, constraints, output shape, check. The check goes last because it is the last thing the reader or the script needs to see, and because it is the part that depends on all the others. Here is a complete ask for the running shared-bills task, built to be validated:

```text
Goal: work out what each of the three of us owes for last year's shared bills.
Constraints: use only the figures below. The set is complete only when it holds each of Jan to Dec exactly once. If a month is missing, repeated or not a month name, stop and say which month. each_pays is the total divided by 3, rounded half up to the cent. Sam pays the remainder: the total minus two times each_pays.
Output shape: one JSON object and nothing else.
  Complete set: {"status": "ok", "months_counted": N, "total": "0.00", "each_pays": "0.00", "sam_pays": "0.00", "check": {"count": N, "sum": "0.00"}}
  Incomplete set: {"status": "stop", "months_counted": N, "reason": "text that names the month"}
Check: fill in check.count and check.sum from the figures before you fill in total.
Figures: Jan 212, Feb 198, Mar 187, Apr 164, May 151, Jun 142, Jul 139, Aug 141, Sep 158, Oct 183, Nov 205, Dec 240
```

Principle, not measured: I have no recorded run that compares one order of these parts with another. Use the order as a convention that keeps your asks comparable, not as a result.

**2. Choose between an example, a constraint and both.**

| You need | Give | What it costs |
| --- | --- | --- |
| A shape that is easy to show and hard to describe | An example | The reply may copy the example's content as well as its shape |
| A rule that has a reason or an exception | A constraint | It says nothing about layout |
| Both a layout and a rule | Both, kept apart | More text, so more to keep consistent |

The anchoring cost is the one people miss. An example carries its values, its length and its wording. Show the shape with values that cannot be real, such as two invented months. Then let the script do the second defence: it re-computes the answer from the input, so a reply that repeats the example's numbers fails. The fixture `bad-copied-example` below does that. Principle, not measured: I did not run an assistant to see how often it copies an example, so the fixture is a hand-written reply and shows what the script would do, not what an assistant does.

**3. Expect the check to be the part that goes missing.** An ask with many constraints and a strict layout gives the reader many things to satisfy. A reply can meet the layout and leave out the check, because the layout still looks complete. Principle, not measured: no recorded run in this guide shows an assistant dropping a check under an over-constrained ask. The defence does not depend on how often it happens. List the check as a required field. A reply without it then fails mechanically.

**4. Validate the reply with a script.** Ask for a schema (a fixed list of fields with fixed types), then check four things in this order:

1. The reply parses as JSON and is one object.
2. It has exactly the expected fields, no more and no fewer, with the expected types. A count such as `months_counted` must be a whole number, so `12.0` is rejected. The figures must name exactly the twelve months Jan to Dec, so twelve distinct names that include a non-month do not count as a complete set.
3. Every value that can be re-computed from the input matches the re-computation.
4. On the stop path, the reason names the problem month.

Run the script on stored replies first, so that you see it accept and reject.

When the validator rejects a reply, send the error text back once and ask for a corrected reply. Allow at most two retries, then stop and report. Do not loosen the validator to make a reply pass.

The validator checks form and re-computable values. It cannot check a judgement, such as whether a summary is fair. For that you need a reviewer ([level 5](../../../journey/05-check-the-work/)).

**5. Re-run a fixed case set when the model or the prompt changes.** A prompt that passes today can fail after a model change, with no edit to your files. Keep a regression check:

1. Fix a case set. Include the normal case and each known awkward input (a repeated month, a missing month).
2. Set the pass criterion before you run. Here it is: every stored reply for every case passes the validator.
3. Pin the model. Use the exact model identifier. If your tool offers a name that always points at the newest version, that name can change the model without any change in your files. Record the identifier with the results.
4. Store the raw replies of each run, with the model identifier, the date and the prompt text.
5. Change the pinned model or the prompt only after the new one passes the same cases.

Two replies per case is too few for a real check. Zero failures in n runs still allows a failure rate of roughly 3 divided by n (the rule of three), which is about 30% at n = 10. ## Failure modes it reduces

- A reply that looks complete but has no check.
- A reply that copies the numbers of the example in the ask.
- A prompt that passes on Monday and fails after the model changes.
- A validator loosened one reply at a time until it accepts anything.

## First step for the maintainer

Take one ask you send often. Write its output shape as a list of fields. Write a 30-line script that rejects a reply with a missing field or a wrong total. Keep five real replies as fixtures, two of them bad.
