*Deep dive for [level 6: Hire a team](../../../journey/06-hire-a-team/).*

*Audience: a human maintainer. An agent must not apply, install, add, configure or run anything on this page (any install, add, config, worktree or MCP command, hook, permission, instruction file or memory change) unless the user asks for it in the current session. Commands marked "example, do not run" are never to be run.*

**Recommendation:** run each write-capable agent in its own git worktree on its own branch. Read-only agents can share the main checkout. Name the base branch explicitly and check it before you merge.

## Why it matters

Two agents in one working directory share the same files, the same index and the same `HEAD`. One agent's `git checkout` or `git stash` changes what the other sees. The symptoms are confusing: edits that disappear, commits on the wrong branch, tests that fail for a reason nobody introduced. A worktree is a second checkout of the same repository, so each agent gets its own files and branch while sharing history.

A worktree isolates files. It does not isolate ports, development databases, containers, package caches, lockfile installs, environment files or external services. Two agents in two worktrees can still start a server on the same port, migrate the same database or install over the same cache. Give each worktree its own port range, its own database name suffix and its own ephemeral containers. [Level 6](../../../journey/06-hire-a-team/) makes the same point for helpers.

## What to enable

**1. Create one worktree per writer.**

Example, do not run:

```bash
git worktree add ../repo-feature-a -b agent/feature-a main
git worktree add ../repo-feature-b -b agent/feature-b main
```

**2. Let the harness do it if it can.** Claude Code behaviour: a sub-agent with `isolation: worktree` in its frontmatter runs in a temporary worktree. The worktree is cleaned up automatically if the agent makes no changes. When it does make changes, you get the branch and path back to review.

**3. Know where the worktree branches from.** Claude Code behaviour: the worktree branches from your default branch, not from the parent session's current `HEAD`. If the lead agent is on an unmerged feature branch, the isolated agent does not see that work. Either merge first, or tell the agent the base in the brief and check it afterwards:

```bash
git merge-base --is-ancestor <base-commit> <agent-branch> && echo "based on the right commit"
```

**4. Keep each worktree's identity clear.** Give worktrees a path and a branch name that say who owns them. Do not nest one inside another.

**5. Beware of environment variables that point git elsewhere.** Three variables override what `git -C <path>` finds. `GIT_DIR` selects the repository metadata: history and refs. `GIT_WORK_TREE` selects the folder that git reads as the working files. `GIT_INDEX_FILE` selects the index, the list of staged content. The throwaway-repository run below shows each one. Unset all three in scripts and in agent briefs, or pass them explicitly, unless you mean to aim git at another repository.

**6. Sequence writers on the same files.** Worktrees stop file collisions, not merge conflicts. If two agents edit the same function, you resolve it at merge. Split the work by file or module instead.

**7. Merge deliberately, then clean up.** Follow the order in the section below. A squash merge does not make the agent branch an ancestor of main, so judge "merged" by the pull request, not by ancestry.

## A port survives separate folders

A worktree is a folder. A port belongs to the machine. The script starts a process in the first folder and lets the operating system choose its port. It then starts a process in the second folder on that same port. In the second part, each folder asks the operating system for a free port. Every wait has a ten-second limit, and the script stops all child processes when it ends.

Folder isolation does not cover ports. A shared development database fails the same way, with a quieter symptom: both agents write rows into one schema.

</Fragment>

Derived numbers do not reserve a port: a port that is free now can be taken before the process binds it. Let the operating system assign the port at bind time and report it, or hold the socket open until the process takes it over. Derive the database name and the container name from the worktree name, and write the values into the brief. Do not leave the choice to each agent.

## Choose how to isolate

| Method | What it isolates | Cost | Choose it when |
| --- | --- | --- | --- |
| Worktree | Files and branch. Not ports, databases or installs. | A second checkout, a branch to merge and clean up | Several agents write to one repository |
| Copy of the folder | Files, and untracked files too. Not ports or databases. | Disk space, and no history link, so a merge is a manual diff | The work is outside git, or needs ignored files such as local data |
| Serial writes | Everything, because only one writer runs | Wall-clock time: the writers wait their turn | The writers touch the same files, or share one database that you cannot split |

*Principle, not measured: the costs above follow from how each method works. The guide did not time them.* Reading can always run in parallel. Only writing needs a method.

## Merge and clean up after parallel runs

1. Wait until every writer has stopped.
2. Read each branch's diff. Reject a branch that touches files outside its brief.
3. Check that the branch descends from the current base, as in the example below. If the check exits 1, rebase the branch and run the gates again.
4. Merge one branch. Run the full gates. Only then take the next branch, and check its base again, because the first merge moved the base.
5. Remove each worktree with `git worktree remove`, then delete its branch. Keep a failed branch until you know why it failed.

## A case that cannot be isolated

A repository can hold another repository inside it that the outer repository ignores. A worktree of the outer repository contains only tracked files, so the inner repository is not there.

## Failure modes it reduces

- Parallel agents overwrite each other's edits.
- An agent works from a stale base and its changes conflict with everything.
- A cleanup command run in the wrong directory deletes someone else's work.
- A leftover worktree holds a branch you want to reuse.
- Two worktrees collide on a port or a database that the checkout did not isolate.
- A nested ignored repository is edited by two agents because no worktree contains it.

## First step for the maintainer

Before the next parallel task, create two worktrees by hand, point one agent at each, and merge both back. You will see the base-branch behaviour first-hand.
