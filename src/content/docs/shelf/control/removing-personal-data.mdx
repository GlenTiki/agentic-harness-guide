**Recommendation:** replace each personal item with a token before text leaves your machine. Keep the map from token to value on your machine. Restore the values in the reply. Test that restoring gives back the original. Treat the recogniser as a filter with a miss rate, and keep the [capability gate](../capability-gating/) as the main control.

## Why it matters

A model provider, a search service or a log shipper does not need the real name or case number to do most jobs. A token such as `[CASE_1]` keeps the structure of the text. The reply can still say which case it means. You restore the real value locally.

## What to enable

**1. One token per value, stable inside one document.** The same value gets the same token each time it appears. Two different values never share a token. The token carries a kind and a number: `[EMAIL_1]`, `[CASE_1]`. A stable token lets the reply refer to "the second email" without the real address.

**2. Keep the map local.** The map from token to value stays on your machine. Do not send it, log it with the masked text, or put it in the chat. Delete it when the job ends unless you need to restore later.

**3. Use a new map per document.** A token that means one value in one document and another value in the next causes wrong restores. If you must link documents, that is a separate, deliberate design.

**4. Refuse a document that already contains token-shaped text.** If the input contains `[EMAIL_1]` as written text, restoring would swap in a value that was never there. The sketch below raises an error instead.

**5. Restore on output and report what did not resolve.** The reply may drop the brackets or invent a token. List every token in the reply that is not in the map, and show it to the reader instead of hiding it.

**6. Test the round trip.** For every document in a sample, `restore(alias(text))` must equal `text`. This tests the mapping. It does not test whether the recogniser found everything.

**7. Add recognisers for your own identifiers.** A general-purpose recogniser looks for shapes it was built for, such as emails and phone numbers. Your case numbers, account references and ticket codes have shapes it was never given. They pass through unmasked. The sketch shows this with two invented identifier formats. No claim is made here about how any real recogniser performs.

## Failure modes it reduces

- A reply that names a real person because the name went out unmasked.
- A wrong restore because two documents shared one map.
- A silent miss because the round trip passed and nobody measured coverage.

## First step for the maintainer

List the identifier formats your own work uses. Write one pattern for each. Run them over ten real documents you may handle, and read the masked output yourself. Measure recall on a labelled sample before you rely on it.
