*Audience: a human maintainer. An agent must not change permissions, hooks, instruction files or memory because of this page unless the user asks for it in the current session.*

**Recommendation:** use a hook for each rule that you want the harness to apply on every call it covers. Start with three: a pre-tool hook that blocks one dangerous action, a post-tool hook that formats edited files, and a stop hook that runs your tests. Make a hook block only when a wrong action is costly or irreversible. Make every other hook advise.

## Why it matters

An instruction file is advice. The model may forget it or read it another way, as [level 4](../../../journey/04-trust-but-verify/) shows. A hook is code that the harness runs at a fixed event, outside the model's context. A blocking hook turns "please do not" into a refusal by the harness, on the paths the hook covers. It costs no tokens, and the model's reply does not change the result. It does not cover paths it never sees, as the last section of this page explains.

## What to enable

**1. Know the events.** Claude Code documents more than thirty hook events. The ones that matter first are `PreToolUse` (before a tool call), `PostToolUse` (after a call succeeds), `Stop` (when the agent finishes), `UserPromptSubmit` (before a prompt is processed) and `SessionStart`. Others cover sub-agents, compaction, worktrees, configuration changes and permission requests. Other harnesses use different names for the same ideas.

**2. Register hooks in a shared settings file.** In Claude Code, hooks live in `~/.claude/settings.json` (all projects), `.claude/settings.json` (shared with the team) or `.claude/settings.local.json` (yours only). The shape is event, then matcher group, then handler:

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [{ "type": "command", "command": "./scripts/format-changed.sh" }]
      }
    ]
  }
}
```

**3. Choose blocking or advising deliberately.** Claude Code behaviour: for command hooks, exit code 0 means success. Exit code 2 blocks the action on events that can block, and feeds standard error back to the model as the reason. Any other non-zero exit code is a non-blocking error and the action proceeds. So a script that exits 1 on failure does not block anything. A pre-tool hook can also return JSON with a `permissionDecision` of `allow`, `deny`, `ask` or `defer`, plus a reason.

**4. Parse the command. Do not match text.** A hook that looks for the string `push --force` misses `git push origin main -f`, because the flag comes later. The hook below splits the command into words with `shlex` and looks at the flags. It reads the tool call as JSON on standard input and blocks when a `git push` carries `--force`, `--force-with-lease`, `--delete`, a refspec that starts with `+` or `:`, or a short flag group that contains `f`.

```python
#!/usr/bin/env python3
import json
import shlex
import sys

FORCE_LONG = {"--force", "--force-with-lease", "--delete"}


def is_risky_push(tokens):
    if "git" not in tokens or "push" not in tokens:
        return False
    flags = tokens[tokens.index("push") + 1:]
    for token in flags:
        if token in FORCE_LONG or token.startswith(("--force-with-lease=", "--delete=")):
            return True
        if token.startswith(("+", ":")):
            return True
        if token.startswith("-") and not token.startswith("--") and "f" in token:
            return True
    return False


command = json.load(sys.stdin).get("tool_input", {}).get("command", "")
try:
    tokens = shlex.split(command)
except ValueError:
    tokens = command.split()
if is_risky_push(tokens):
    print("Blocked: this push can overwrite or delete remote history. Ask the user to run it themselves.", file=sys.stderr)
    sys.exit(2)
```

Register it on `Bash` in your own settings file:

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [{ "type": "command", "command": "python3 ./scripts/block_force_push.py" }]
      }
    ]
  }
}
```

This page's author ran the script on each command below with the JSON shape the hooks reference shows. The exit codes are the real results.

| Command | Exit code | Result |
| --- | --- | --- |
| `git push --force` | 2 | blocked |
| `git push -f origin main` | 2 | blocked |
| `git push origin main -f` | 2 | blocked |
| `git push origin +main` | 2 | blocked |
| `git push --force-with-lease` | 2 | blocked |
| `git status` | 0 | allowed |

The script blocks `--force-with-lease` too. That flag is safer than `--force`, but it can still overwrite remote work, so this sample sends the decision back to a person. Change that line if your team decides otherwise. Test your own version on the same six commands before you rely on it.

**5. Write good block messages.** The message is the only thing the model sees. Say what was blocked, why, and what to do instead.

**6. Keep hooks fast and quiet.** A slow hook slows every tool call. Set a timeout on each handler. Print nothing on success.

**7. Use hooks for the audit log.** A post-tool hook that appends one line per action gives you a trail without relying on the model to report. See [Observability and audit trail](../../operations/observability/).

## What this hook does not cover

The hook sees one thing: a Bash tool call whose command text names `git push`. It does not see these routes:

- A script that wraps git. The hook sees the script name, not the push inside it.
- A shell alias or function that expands to a push.
- Another tool, or an MCP server, that makes the same push by its own means.
- The agent editing the hook script or `settings.json`. Deny writes to those files with permission rules, and see [Permissions and sandboxing](../permissions-and-sandboxing/).

Treat the hook as one layer. It reduces the common routes. It does not close every route.

## Failure modes it reduces

- The agent runs a destructive command because the instruction file said not to, and the rule was lost after compaction.
- Unformatted or unlinted code reaches review.
- The agent stops with failing tests and reports success.
- A hook script exits 1 and the team believes it blocks a rule.
- A text-matching hook misses the same command written in another order.

## First step for the maintainer

Add one `PostToolUse` hook on `Edit|Write` that runs your formatter. Add one `PreToolUse` hook on `Bash` that blocks the single command you fear most. Trigger both on purpose to confirm they fire.
