*Audience: a human maintainer. An agent must not apply, install, add, configure or run anything on this page (any install, add, config, worktree or MCP command, hook, permission, instruction file or memory change) unless the user asks for it in the current session. Commands marked "example, do not run" are never to be run.*

**Recommendation:** use a hook for each rule that you want the harness to apply on every call it covers. Start with three hooks. A pre-tool hook blocks one dangerous action. A post-tool hook formats edited files. A stop hook runs your tests. Make a hook block only when a wrong action is costly or irreversible. Make every other hook advise.

## Why it matters

An instruction file is advice, and nothing guarantees the model follows it. That is a principle. [Level 4](../../../journey/04-trust-but-verify/) measured a planted line, not forgetting. A hook is code that the harness runs at a fixed event, outside the model's context. A blocking hook turns "please do not" into a refusal by the harness, on the paths the hook covers. It costs no tokens, and the model's reply does not change the result. It does not cover paths it never sees, as the last section of this page explains.

## What to enable

**1. Know the events.** Claude Code documents more than thirty hook events. The ones that matter first are `PreToolUse` (before a tool call), `PostToolUse` (after a call succeeds) and `Stop` (when the agent finishes). Two more are `UserPromptSubmit` (before a prompt is processed) and `SessionStart`. Others cover sub-agents, compaction, worktrees, configuration changes and permission requests. Other harnesses use different names for the same ideas.

**2. Register hooks in a shared settings file.** In Claude Code, hooks live in `~/.claude/settings.json` (all projects), `.claude/settings.json` (shared with the team) or `.claude/settings.local.json` (yours only). The shape is event, then matcher group, then handler:

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [{ "type": "command", "command": "bash \"${CLAUDE_PROJECT_DIR}/.claude/hooks/format-changed.sh\"" }]
      }
    ]
  }
}
```

**3. Choose blocking or advising deliberately.** Claude Code behaviour: for command hooks, exit code 0 means success. Exit code 2 blocks the action on events that can block, and feeds standard error back to the model as the reason. Any other non-zero exit code is a non-blocking error and the action proceeds. So a script that exits 1 on failure does not block anything. A pre-tool hook can also return JSON with a `permissionDecision` of `allow`, `deny`, `ask` or `defer`, plus a reason.

**4. Parse the command. Do not match text.** A hook that looks for the string `push --force` misses `git push origin main -f`, because the flag comes later. The sample below splits the command into words with `shlex` and looks at the flags. It reads the tool call as JSON on standard input. It is a teaching sample, not a security boundary.

The sample blocks a `git push` that carries any of these:

- `--force`, `--force-with-lease`, `--force-if-includes`, `--delete`, `--mirror` or `--prune`.
- Any abbreviation of those that is five or more characters long, counting the two dashes. So `--del` and `--forc` are blocked.
- A short flag group that contains `f` or `d`.
- A refspec that starts with `+` or `:`.

The sample also handles these cases. It recognises `git` by its file name, so `/usr/bin/git` and `env git` count, and a leading `(`, `{`, `$(` or backtick is ignored. It also looks inside a quoted string, so `sh -c "git push -f"` and `bash -c '...'` are blocked. It exits 2 when it cannot read the call. It blocks nothing else.

```python
#!/usr/bin/env python3
import json
import os
import shlex
import sys

RISKY_LONG = ("--force", "--force-with-lease", "--force-if-includes", "--delete", "--mirror", "--prune")
RISKY_SHORT = "fd"


def is_risky_flag(token):
    token = token.rstrip(")}`")
    if token.startswith("--"):
        name = token.split("=")[0]
        return len(name) >= 5 and any(long.startswith(name) for long in RISKY_LONG)
    if token.startswith("-"):
        return any(letter in token[1:] for letter in RISKY_SHORT)
    return token.startswith(("+", ":"))


def is_risky_push(tokens):
    for index, token in enumerate(tokens):
        if " " in token and is_risky_push(shlex.split(token)):
            return True
        if os.path.basename(token.lstrip("({$`")) == "git" and "push" in tokens[index:]:
            after_push = tokens[tokens.index("push", index) + 1:]
            return any(is_risky_flag(flag) for flag in after_push)
    return False


def main():
    try:
        command = json.load(sys.stdin)["tool_input"]["command"]
        risky = is_risky_push(shlex.split(command))
    except (ValueError, KeyError, TypeError, AttributeError) as error:
        print(f"Blocked: the hook could not read this call ({error}).", file=sys.stderr)
        sys.exit(2)
    if risky:
        print("Blocked: this push can overwrite or delete remote history. Ask the user to run it themselves.", file=sys.stderr)
        sys.exit(2)


if __name__ == "__main__":
    main()
```

The same file is at `examples/hook-sample/block_force_push.py`. A test file next to it, `test_matrix.py`, runs it on every row of the table below and prints one line per row.

**Where to put it and how to register it.** Save the script as `.claude/hooks/block_force_push.py` in your project. Register it with the project-root variable, not a relative path. The hooks reference defines it in these words: "`${CLAUDE_PROJECT_DIR}`: the project root where the session started." Its own examples use the form `${CLAUDE_PROJECT_DIR}/.claude/hooks/block-rm.sh`. The same page says that handlers "run in the current directory", so a relative path breaks when the session moves to another directory.

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [{ "type": "command", "command": "python3 \"${CLAUDE_PROJECT_DIR}/.claude/hooks/block_force_push.py\"" }]
      }
    ]
  }
}
```

Quote the expanded path, as the example does. A shell splits an unquoted path that contains a space into several words. Run through `sh -c` in a scratch folder with a space in its name, the quoted command ran the script, and the unquoted one exited 2 because Python could not open the split path. On that hook, exit 2 blocks the call. Name the interpreter (`python3` or `bash`) in the command, so the script needs no executable permission. If you run a script directly instead, run `chmod +x` on it first.

**A broken hook can block every Bash call, or do nothing.** A missing Python script exits with code 2, which blocks. A missing shell script exits with code 127, which is a non-blocking error, so the hook silently does nothing.

**Fail safe, and what it costs.** The sample exits 2 when it cannot read the call, because a guard that quietly lets everything through is worse. The cost is that every Bash call is blocked if the harness ever changes the shape of the JSON it sends. The block lasts until you fix the script or switch the hook off. The hooks reference explains how to switch hooks off. It says: "To temporarily disable all hooks without removing them, set `"disableAllHooks": true` in your settings file." You can also delete the entry. Keep a second window open while you test, so you can undo the change.

**Test it in this order.**

1. Check that the file exists: `test -f .claude/hooks/block_force_push.py`.
2. Pipe a call to it by hand: `echo '{"tool_input":{"command":"git status"}}' | python3 .claude/hooks/block_force_push.py; echo $?` must print 0. Then try `git push --force` and expect 2 and the block message.
3. Register it in a throwaway repository first, not your real settings.
4. In that session, run `git status` and confirm it is allowed.
5. Ask the assistant for `git push --force` to a local bare repository you created for the test, and confirm you see the block message.
6. Only then register it in your real settings.

## What this hook does not cover

The hook sees one thing: a Bash call whose command text, once split into words, shows `git`, then `push`, then a risky flag. The routes below get past it.

Why each route gets past the script:

- Variable expansion: the script sees the text `$F` or `$g`, not `-f` or `git`.
- ANSI-C quoting: `$'\x2df'` is the text `-f` to the shell and a different word to the script.
- Command substitution inside quotes: `"$(echo --force)"` becomes `--force` only when the shell runs it.
- A shortened long option: git accepts `--de` for `--delete`. The sample only checks abbreviations of five or more characters.
- An alias that expands to a push without the word `push`, such as `git p -f`.
- The dashed form: the script looks for a word named `git`, and `git-push` is a different word.
- Code that runs a push: `python3 -c` with `os.system`, and any wrapper script such as `./deploy.sh`. The hook sees the script name, not the push inside it.
- Another tool, or an MCP server, that makes the same push by its own means. The matrix does not run this one.
- The agent editing the hook script or `settings.json`. The matrix does not run this one. Deny writes to those files with permission rules (see [Permissions and sandboxing](../permissions-and-sandboxing/)).

Treat the hook as one layer. It reduces the common routes. It does not close every route.

## Traps that bite in practice

### A pipe into tail hides the exit status

A shell pipeline returns the exit status of its last command. A check piped into `tail` therefore reports the status of `tail`, which succeeds. Capture the output to a file, keep the status, then show the tail.

### A one-shot stop reminder

A stop hook that blocks every time never lets the agent finish. A one-shot reminder keys the block to the session identifier. It is a reminder, not a quality gate: it never looks at the test result. ### A stop gate that checks the result

A real gate runs the tests at every stop and reads the result. If the tests fail, it blocks and returns the failure text to the agent. It counts the failed attempts for the session. After three, it lets the agent stop and writes an escalation file that holds the last failure output, so a person reviews the session. The limit of three is a starting value: it bounds the cost of a loop, so tune it on your own sessions. The script reads the test command from `TEST_COMMAND`.

### Three outcomes, and which exit code means "deliberate"

A pre-action check has three outcomes. A hard deny stops the call. A soft deny stops the call and tells the model why, so it can choose another route. A pass lets the call run. Your tool decides which exit code or output means which. In Claude Code, exit code 2 blocks and sends standard error back, and any other non-zero code does not block (see item 3 above). Check your own tool's docs before you rely on a code, because another harness may treat 1 as the deliberate denial.

### Every blocking check needs a bypass route

A block with no way round gets disabled the first time it is wrong. Give each blocking check a documented bypass that a person controls, such as an environment variable the agent cannot set, or a one-line change to the settings file. Log each use of it. The bypass belongs in the check's block message, so the person sees it when the check fires.

### The wrong repository

A hook that asks git about a repository can answer about another one. Git reads `GIT_DIR`, `GIT_WORK_TREE` and `GIT_INDEX_FILE` from the environment, and `git -C` does not override them. If a session started inside a nested repository, the hook inspects that one.

### Several hooks and latency

The docs say: "When an event fires, its matching hooks run in parallel." So the wait for an event is about the slowest hook, not the sum. The part of the page read on 2026-10-26 did not state how conflicting decisions combine, such as one hook denying and another allowing. Not verified. Test it with two hooks that disagree before you rely on an order. The same page gives command hooks a default timeout of 600 seconds, so set a shorter one on each. This guide measured no harness-level latency and no parallel-hook latency. The only timings are the standalone script runs in the chart above.

## Failure modes it reduces

- The agent runs a destructive command because the instruction file said not to, and the rule was lost after compaction.
- Unformatted or unlinted code reaches review.
- The agent stops with failing tests and reports success.
- A hook script exits 1 and the team believes it blocks a rule.
- A hook path that no longer resolves blocks every Bash call, or silently does nothing, depending on the script type.
- A text-matching hook misses the same command written in another order.

## First step for the maintainer

Add one `PostToolUse` hook on `Edit|Write` that runs your formatter. Add one `PreToolUse` hook on `Bash` that blocks the single command you fear most. Trigger both on purpose to confirm they fire.
