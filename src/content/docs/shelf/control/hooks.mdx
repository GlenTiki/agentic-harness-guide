*Audience: a human maintainer. An agent must not apply, install, add, configure or run anything on this page (any install, add, config, worktree or MCP command, hook, permission, instruction file or memory change) unless the user asks for it in the current session. Commands marked "example, do not run" are never to be run.*

**Recommendation:** use a hook for each rule that you want the harness to apply on every call it covers. Start with three: a pre-tool hook that blocks one dangerous action, a post-tool hook that formats edited files, and a stop hook that runs your tests. Make a hook block only when a wrong action is costly or irreversible. Make every other hook advise.

## Why it matters

An instruction file is advice. The model may forget it or read it another way, as [level 4](../../../journey/04-trust-but-verify/) shows. A hook is code that the harness runs at a fixed event, outside the model's context. A blocking hook turns "please do not" into a refusal by the harness, on the paths the hook covers. It costs no tokens, and the model's reply does not change the result. It does not cover paths it never sees, as the last section of this page explains.

## What to enable

**1. Know the events.** Claude Code documents more than thirty hook events. The ones that matter first are `PreToolUse` (before a tool call), `PostToolUse` (after a call succeeds), `Stop` (when the agent finishes), `UserPromptSubmit` (before a prompt is processed) and `SessionStart`. Others cover sub-agents, compaction, worktrees, configuration changes and permission requests. Other harnesses use different names for the same ideas.

**2. Register hooks in a shared settings file.** In Claude Code, hooks live in `~/.claude/settings.json` (all projects), `.claude/settings.json` (shared with the team) or `.claude/settings.local.json` (yours only). The shape is event, then matcher group, then handler:

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [{ "type": "command", "command": "${CLAUDE_PROJECT_DIR}/.claude/hooks/format-changed.sh" }]
      }
    ]
  }
}
```

**3. Choose blocking or advising deliberately.** Claude Code behaviour: for command hooks, exit code 0 means success. Exit code 2 blocks the action on events that can block, and feeds standard error back to the model as the reason. Any other non-zero exit code is a non-blocking error and the action proceeds. So a script that exits 1 on failure does not block anything. A pre-tool hook can also return JSON with a `permissionDecision` of `allow`, `deny`, `ask` or `defer`, plus a reason.

**4. Parse the command. Do not match text.** A hook that looks for the string `push --force` misses `git push origin main -f`, because the flag comes later. The sample below splits the command into words with `shlex` and looks at the flags. It reads the tool call as JSON on standard input. It is a teaching sample, not a security boundary.

The sample blocks a `git push` that carries any of these: `--force`, `--force-with-lease`, `--force-if-includes`, `--delete`, `--mirror` or `--prune`; any abbreviation of those that is five or more characters long counting the two dashes (so `--del` and `--forc` are blocked); a short flag group that contains `f` or `d`; or a refspec that starts with `+` or `:`. It recognises `git` by its file name, so `/usr/bin/git` and `env git` count, and a leading `(`, `{`, `$(` or backtick is ignored. It also looks inside a quoted string, so `sh -c "git push -f"` and `bash -c '...'` are blocked. It exits 2 when it cannot read the call. It blocks nothing else.

```python
#!/usr/bin/env python3
import json
import os
import shlex
import sys

RISKY_LONG = ("--force", "--force-with-lease", "--force-if-includes", "--delete", "--mirror", "--prune")
RISKY_SHORT = "fd"


def is_risky_flag(token):
    token = token.rstrip(")}`")
    if token.startswith("--"):
        name = token.split("=")[0]
        return len(name) >= 5 and any(long.startswith(name) for long in RISKY_LONG)
    if token.startswith("-"):
        return any(letter in token[1:] for letter in RISKY_SHORT)
    return token.startswith(("+", ":"))


def is_risky_push(tokens):
    for index, token in enumerate(tokens):
        if " " in token and is_risky_push(shlex.split(token)):
            return True
        if os.path.basename(token.lstrip("({$`")) == "git" and "push" in tokens[index:]:
            after_push = tokens[tokens.index("push", index) + 1:]
            return any(is_risky_flag(flag) for flag in after_push)
    return False


def main():
    try:
        command = json.load(sys.stdin)["tool_input"]["command"]
        risky = is_risky_push(shlex.split(command))
    except (ValueError, KeyError, TypeError, AttributeError) as error:
        print(f"Blocked: the hook could not read this call ({error}).", file=sys.stderr)
        sys.exit(2)
    if risky:
        print("Blocked: this push can overwrite or delete remote history. Ask the user to run it themselves.", file=sys.stderr)
        sys.exit(2)


if __name__ == "__main__":
    main()
```

The same file is at `examples/hook-sample/block_force_push.py`. A test file next to it, `test_matrix.py`, runs it on every row of the table below and prints one line per row.

**Where to put it and how to register it.** Save the script as `.claude/hooks/block_force_push.py` in your project. Register it with the project-root variable, not a relative path. The hooks reference defines it in these words: "`${CLAUDE_PROJECT_DIR}`: the project root where the session started." Its own examples use the form `${CLAUDE_PROJECT_DIR}/.claude/hooks/block-rm.sh`. The same page says that handlers "run in the current directory", so a relative path breaks when the session moves to another directory.

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [{ "type": "command", "command": "python3 ${CLAUDE_PROJECT_DIR}/.claude/hooks/block_force_push.py" }]
      }
    ]
  }
}
```

**A broken hook can block every Bash call.** Run on a script that does not exist, `python3` exits with code 2. Code 2 is the blocking code, so a missing Python script blocks every Bash call. Run on a missing shell script, `sh` exits 127. That code is a non-blocking error, so the hook silently does nothing. Both results are real runs from 2026-10-22: `python3 ./missing.py; echo $?` printed 2 and `sh ./missing.sh; echo $?` printed 127.

**Fail safe, and what it costs.** The sample exits 2 when it cannot read the call, because a guard that quietly lets everything through is worse. The cost is that if the harness ever changes the shape of the JSON it sends, every Bash call is blocked until you fix the script or switch the hook off. To switch hooks off, the hooks reference says: "To temporarily disable all hooks without removing them, set `"disableAllHooks": true` in your settings file." You can also delete the entry. Keep a second window open while you test, so you can undo the change.

**Test it in this order.**

1. Check that the file exists: `test -f .claude/hooks/block_force_push.py`.
2. Pipe a call to it by hand: `echo '{"tool_input":{"command":"git status"}}' | python3 .claude/hooks/block_force_push.py; echo $?` must print 0. Then try `git push --force` and expect 2 and the block message.
3. Register it in a throwaway repository first, not your real settings.
4. In that session, run `git status` and confirm it is allowed.
5. Ask the assistant for `git push --force` to a local bare repository you created for the test, and confirm you see the block message.
6. Only then register it in your real settings.

The script blocks `--force-with-lease` too. That flag is safer than `--force`, but it can still overwrite remote work, so this sample sends the decision back to a person. Change that line if your team decides otherwise.

**5. Write good block messages.** The message is the only thing the model sees. Say what was blocked, why, and what to do instead.

**6. Keep hooks fast and quiet.** A slow hook slows every tool call. Set a timeout on each handler. Print nothing on success.

**7. Use hooks for the audit log.** A post-tool hook that appends one line per action gives you a trail without relying on the model to report. See [Observability and audit log](../../operations/observability/).

## What this hook does not cover

The hook sees one thing: a Bash tool call whose command text, once split into words, shows `git` followed by `push` and a risky flag. The matrix above covers none of the routes below. Each row in this table is a real run of the sample on 2026-10-24, and exit code 0 means the sample let it through. Against a throwaway repository on the same date, git also ran the rows for the variable command name, the command substitution, `--de`, the command-line alias and the dashed form.

| Command | Exit code | Result |
| --- | --- | --- |
| `F=-f; git push $F` | 0 | allowed |
| `g=git; $g push -f origin main` | 0 | allowed |
| `git push origin main $'\x2df'` | 0 | allowed |
| `git push origin main "$(echo --force)"` | 0 | allowed |
| `git push --de origin x` | 0 | allowed |
| `git -c alias.p=push p -f origin main` | 0 | allowed |
| `/usr/libexec/git-core/git-push -f origin main` | 0 | allowed |
| `python3 -c 'import os;os.system("git push -f")'` | 0 | allowed |
| `./deploy.sh` | 0 | allowed |

In words:

- Variable expansion: `F=-f; git push $F` and `g=git; $g push -f`. The script sees the text `$F` or `$g`, not `-f` or `git`.
- ANSI-C quoting: `$'\x2df'` is the text `-f` to the shell and a different word to the script.
- Command substitution inside quotes: `"$(echo --force)"` becomes `--force` only when the shell runs it. The script sees the unexpanded text.
- A shortened long option: git accepts `--de` for `--delete` and deletes the branch. The sample only checks abbreviations of five or more characters.
- An alias, here set on the command line, that expands to a push without the word `push` in the command, such as `git p -f`.
- The dashed form of the command: the script looks for a word named `git`, and `git-push` is a different word.
- Code that runs a push: `python3 -c` with `os.system`, and any wrapper script such as `./deploy.sh`. The hook sees the script name, not the push inside it.
- Another tool, or an MCP server, that makes the same push by its own means. The matrix does not run this one.
- The agent editing the hook script or `settings.json`. The matrix does not run this one. Deny writes to those files with permission rules, and see [Permissions and sandboxing](../permissions-and-sandboxing/).

Treat the hook as one layer. It reduces the common routes. It does not close every route.

## Failure modes it reduces

- The agent runs a destructive command because the instruction file said not to, and the rule was lost after compaction.
- Unformatted or unlinted code reaches review.
- The agent stops with failing tests and reports success.
- A hook script exits 1 and the team believes it blocks a rule.
- A hook path that no longer resolves blocks every Bash call, or silently does nothing, depending on the script type.
- A text-matching hook misses the same command written in another order.

## First step for the maintainer

Add one `PostToolUse` hook on `Edit|Write` that runs your formatter. Add one `PreToolUse` hook on `Bash` that blocks the single command you fear most. Trigger both on purpose to confirm they fire.
