*Deep dive for [level 4: Trust, but verify](../../../journey/04-trust-but-verify/).*

*Audience: a human maintainer. An agent must not apply, install, add, configure or run anything on this page (any install, add, config, worktree or MCP command, hook, permission, instruction file or memory change) unless the user asks for it in the current session. Commands marked "example, do not run" are never to be run.*

**Recommendation:** combine three layers. Permission rules decide which tool calls need approval. A sandbox limits what shell commands can reach at the operating system level. A container or virtual machine bounds everything else. Start with deny rules for secrets and a sandbox with an empty network allow list.

## Why it matters

Approval prompts do not scale. *Principle, not measured:* a person who is asked for approval often can stop reading each prompt. This is approval fatigue, and [level 4](../../../journey/04-trust-but-verify/) covers it. Rules and a sandbox let the safe majority of actions run unattended and put the human attention on the few that matter.

## What to enable

GitHub Copilot CLI is the worked example on this page. The ideas apply to any agent; the flag and setting names do not.

**1. Deny first.** In Copilot CLI, a `--deny-tool` option wins over every allow option. Deny the commands you never want run, even when you allow other tools without a prompt. Example, do not run:

```bash
copilot --allow-tool='shell(git)' --deny-tool='shell(git push)' --deny-tool='shell(rm)'
```

Quoted line: "This option takes precedence over the `--allow-all-tools` and `--allow-tool` options." GitHub Copilot CLI on that date: Version not checked. The docs page states no version of its own.</p>

Claude Code differs: its rules live in a settings file, and they are evaluated deny, then ask, then allow, with the first match winning. A rule can also name a file, so a secret can be denied by path:

```json
{
  "permissions": {
    "allow": ["Bash(npm run lint)", "Bash(npm run test *)"],
    "deny": ["Read(./.env)", "Read(./.env.*)", "Read(./secrets/**)"]
  }
}
```

**2. Allow narrowly.** Allow exact commands that you run all the time. Avoid a grant over a whole tool. In Copilot CLI, the approval prompt offers to approve a tool "for the rest of the running session". The docs warn that approving `rm ./this-file.txt` that way lets the agent run any `rm` command, for example `rm -rf ./*`, until the session ends.

<p class="verified">Docs page fetched on 2026-11-23: https://docs.github.com/en/copilot/concepts/agents/about-copilot-cli. Quoted line: "If you choose this option, you are allowing Copilot to use this tool in any way it thinks is appropriate." GitHub Copilot CLI on that date: Version not checked. The docs page states no version of its own.</p>

A rule that matches command text matches the forms it names and no others. The same program invoked in another form may not match. The Claude Code permissions documentation shows that `Bash(git push *)` does not match `git -C . push origin main`. Copilot CLI documents subcommand rules for `git` and `gh` only. Not checked against current docs: how Copilot CLI matches other spellings of the same command. Rely on the sandbox for isolation, and see [Hooks](../hooks/) for a check that parses the command.

**An allow rule only skips the prompt.** In Copilot CLI's manual approval mode, a tool request that is not already allowed asks you. An allow list does not refuse everything else. It removes the prompt for the calls it names. Test that a call you did not list still asks or is refused.

<p class="verified">Docs page fetched on 2026-11-23: https://docs.github.com/en/copilot/concepts/agents/about-copilot-cli. Quoted line: "In manual approval mode, Copilot asks for your approval when a tool request isn't already allowed." GitHub Copilot CLI on that date: Version not checked. The docs page states no version of its own.</p>

Claude Code differs: in its auto mode a classifier reviews an unmatched call, and the call can run with no prompt. The permission modes page says: "With Claude Code v2.1.283 or later, auto mode is the built-in starting permission mode for interactive terminal and VS Code sessions." Only its `dontAsk` mode refuses an unmatched call: "Auto-denies every call that would otherwise prompt".

**3. Turn on the sandbox.** Copilot CLI's local sandbox is off by default. Until you enable it, shell commands run with your full access. `/sandbox enable` turns it on for this and future sessions. It covers shell commands, file search and, by default, local MCP servers and language servers. Its settings grant or deny paths, and allow or deny network hosts.

<p class="verified">Docs page fetched on 2026-11-23: https://docs.github.com/en/copilot/concepts/security-governance-and-network-settings/about-cloud-and-local-sandboxes. Quoted line: "Local sandboxing is turned off by default." GitHub Copilot CLI on that date: Version not checked. The docs page states no version of its own.</p>

Claude Code differs in detail. Its sandbox covers shell commands only, and its network allow list starts empty. A command that fails in the sandbox can be retried outside it, and a matching allow rule approves that retry with no prompt. Set `sandbox.allowUnsandboxedCommands` to `false` to turn the retry off.

**4. Know what the sandbox does not cover.** In Copilot CLI, the built-in file tools run inside the CLI process, which is not sandboxed. They check the sandbox policy themselves "on a best-effort basis". Remote MCP servers are never sandboxed. Claude Code is similar: its built-in file and web tools, hooks and local MCP servers run outside its sandbox. A sandbox therefore bounds what a shell command can reach. It does not bound the agent's own file tools.

<p class="verified">Docs page fetched on 2026-11-23: https://docs.github.com/en/copilot/concepts/security-governance-and-network-settings/about-cloud-and-local-sandboxes. Quoted line: "Because the CLI itself is not sandboxed, the operating-system sandbox never sees the file operations these tools perform and cannot constrain them." GitHub Copilot CLI on that date: Version not checked. The docs page states no version of its own.</p>

**5. Do not use "skip all prompts" modes on a machine you care about.** In Copilot CLI these are `--allow-all-tools`, `--allow-all`, `--yolo` and the `/yolo` slash command. Run them only inside a disposable container or virtual machine with no credentials.

**6. Launch only from a directory you trust.** Copilot CLI asks you to trust the launch directory and everything below it. It asks again before it works on files in another directory. The docs call this scoping heuristic: it does not guarantee that files outside the trusted directories are protected.

<p class="verified">Docs page fetched on 2026-11-23: https://docs.github.com/en/copilot/concepts/agents/about-copilot-cli. Quoted line: "Scoping of permissions is heuristic and GitHub does not guarantee that all files outside trusted directories will be protected." GitHub Copilot CLI on that date: Version not checked. The docs page states no version of its own.</p>

**7. Check where settings come from.** Settings can come from an administrator, the command line, the project and your user file. Find which source wins in your agent before you rely on a rule. In Copilot CLI, if enterprise managed settings require the sandbox, ordinary settings and startup options cannot turn it off. In Claude Code, managed settings override command-line settings, which override project-local, shared project and user settings.

**8. Control network egress separately.** Prefer an allow list of hosts over a deny list.

**9. Protect the files that constrain the agent.** The agent can edit what constrains it. If it can write to its settings file, to a hook file such as `.github/hooks/*.json` or to your capability registry, it can loosen its own limits. Deny writes to those paths where your agent supports it. Add a file-integrity check or a CI check that fails when they change without review. This is the mechanism behind "turning off a safety control" in the [approval list](../../operations/human-in-the-loop/). Not checked against current docs: whether Copilot CLI guards its own configuration files. Claude Code does: its sandbox denies shell writes to the `.claude` settings files, `.claude/hooks` and `.mcp.json`, and an `Edit` deny rule covers the file tools and the shell file commands it recognises. A script that opens the file itself gets past a deny rule, and a person can still approve a prompt. That is why the integrity or CI check matters more than the deny rule.

## A deny rule that misses an equivalent command

The page above says a rule matches the command text as written. The matcher below makes that visible. It is a teaching sketch, not any agent's matcher. It tests a text rule, `Bash(rm -rf *)`, as a glob over the command string. A second check, written the way the [hooks page](../hooks/) suggests, splits the command into words first.

Source for these excerpts: [matcher.py](https://github.com/GlenTiki/agentic-harness-guide/blob/main/examples/deny-rule-bypass/matcher.py).

Here is the teaching text matcher. It uses Python’s `fnmatch` module; `DENY_RULES` contains `Bash(rm -rf *)` and `Read(./.env)`.

```python
def text_rule_denies(command, tool, rules=DENY_RULES):
    for rule in rules:
        rule_tool, pattern = rule[:-1].split("(", 1)
        if rule_tool.lower() == tool and fnmatch.fnmatchcase(command, pattern):
            return True
    return False
```

The comparison checker uses `shlex.split`, looks for a program whose basename is `rm`, combines its short flags and requires both `r` and `f`. It also examines space-containing arguments, which catches this fixture’s shell wrapper. This is a limited sketch, not a shell interpreter or any agent's implementation. The command strings are inspected, not executed.

### Which layer for which risk

Constructed. Three sample risks and the layer that fits each. The reasoning follows from the example above and from the sandbox scope in item 4. The rule column uses Claude Code's file rules; Copilot CLI's command-line options name tools, not files. It is a design choice, not a measurement.

| Risk | Rule | Hook | Sandbox |
| --- | --- | --- | --- |
| The agent reads `.env` | Deny `Read(./.env)`. It covers the file tool and shell file commands Claude Code recognises, such as `cat` | A hook cannot see file reads that the shell does by other means | With the sandbox on, the same rule also stops a script that opens the file |
| The agent force-pushes | An `ask` rule for the common spelling | A hook that parses the command, with its [known bypasses](../hooks/#what-this-hook-does-not-cover) | None: the push uses an allowed network route. Limit credentials instead |
| A script the agent runs sends data out | None: the command text looks harmless | Weak: it sees the script name only | Primary: an empty network allow list |

Read the table by asking what the control can see. A rule sees a tool name and a text pattern. A hook sees the whole call and can run code on it. A sandbox sees what the process does, whatever it was called.

## Failure modes it reduces

- A prompt-injected command reads your cloud credentials and sends them out.
- A build script the agent runs writes outside the repository.
- Approval fatigue leads to a blanket "always allow".
- A shared repository ships a settings file that quietly widens permissions.
- The agent edits its own settings or hook script to remove a limit.

## First step for the maintainer

Add the deny options above, enable the sandbox and allow only the network hosts your build needs. Then ask the agent for a command you did not allow, and check that it asks or is refused. In Claude Code, also turn off the unsandboxed retry from item 3, because the sample `allow` rules would otherwise approve a retry of a failing test command outside the sandbox.
