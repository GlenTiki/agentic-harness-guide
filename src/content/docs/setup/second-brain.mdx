## The weak spot it targets

**Your notes and the agent's memory live apart.** On Monday you write meeting notes in a notes app. On Tuesday you ask the [agent](../../glossary/#agent) to draft the follow-up email. It knows nothing about the meeting, so you paste the notes. On Friday another session needs the same decision, and you paste them again. Each paste is a manual copy, and each copy can go stale.

## How it works

People who manage their own notes call the store a [second brain](../../glossary/#second-brain). They solved most of this before agents existed, and two of their ideas carry over almost unchanged.

Tiago Forte's CODE method is "a proven process for consistently turning the information you consume into creative output and concrete results", in his words on the [Building a Second Brain overview](https://fortelabs.com/blog/basboverview/). The letters stand for Capture, Organise, Distil and Express. His [PARA](https://fortelabs.com/blog/para/) method sorts every note into Projects, Areas, Resources and Archives. He calls this "organize by actionability": you file a note by when you will use it, not by its subject.

The table maps each step to a part of an agent setup. It is the design. My setup runs only the raw folder, the curated folders and the index.

| Step | For you | For the agent |
| --- | --- | --- |
| Capture | Write it down fast, unsorted. | A raw folder: journal entries, ideas, drafts. The agent appends here and never edits. |
| Organise | File by when you act on it. | Projects: one folder per active project, with its spec. Areas: ongoing responsibilities, such as a team you run, each with its standing facts. Resources: reference material, including lasting facts about tools and preferences. Archives: finished work. |
| Distil | Keep the part that matters. | One fact per note, with a one-line description. The [memory page](../memory/) gives the note rules. |
| Express | Make something with it. | The agent reads the notes to draft the email, the spec or the status update. |

The last row is the point. You capture a fact once, and every later task can use it. I call this "capture once, use many times".

### Two readers, one store

The store has two readers, so it needs two kinds of help.

1. For you, each note links to related notes. The [Zettelkasten introduction](https://zettelkasten.de/introduction/) describes this as "a personal tool for thinking and writing" with "hypertextual features to make a web of thoughts possible".
2. For the agent, a search index finds the few notes that match a prompt. The [relevance page](../relevance-and-reranking/) shows how the search works and where it misses.

<p class="verified">Docs page fetched on 2026-11-16: https://zettelkasten.de/introduction/. Quoted line: "A Zettelkasten is a personal tool for thinking and writing. It has hypertextual features to make a web of thoughts possible."</p>

I keep the notes as Markdown files in a folder, so both readers use them with no export step. A notes app that keeps notes in its own database can also work, if a connector gives the agent access to them.

Andy Matuschak's [Evergreen notes](https://notes.andymatuschak.org/Evergreen_notes) "are written and organized to evolve, contribute, and accumulate over time, across projects". For an agent, that means one of the [note rules](../memory/#rules-for-the-notes-themselves): edit the old note when a fact changes.

## End-to-end flow

1. During the day, you and the agent append captures to the raw folder.
2. At the end of a session, the agent proposes distilled notes: one fact each, with a source line.
3. You accept or reject each note. Accepted notes go into the right PARA folder.
4. The index rebuilds from the folders. It must leave out private files. My indexer does not do this yet.
5. The next prompt searches the index. The best few notes reach the agent as hints.
6. When a session proves a note wrong, the agent proposes an edit to that note.

## What this does not do

- It does not decide what matters. In the design, you approve every distilled note.
- It does not keep notes fresh. A stale note can outrank a fresh one, as the [memory shelf page](../../shelf/context/memory/) explains.
- It does not protect private data on its own. A test must prove that the indexer skips private files.
- I have not measured whether it saves time. The case for it is the repeated paste, which you can count in your own week.

## When to skip it

A second brain costs a capture habit and a weekly tidy. Ask three questions before you build one.

- **Will a later task read the notes?** If the work is a one-off, the capture is wasted.
- **Are the notes still few?** Then skip the index. Pick the notes for each task by hand. Search adds a part that can miss, so add it when picking by hand gets slow.
- **Did you paste the same context twice?** Then build it. The second paste shows that a fact has more than one use.
