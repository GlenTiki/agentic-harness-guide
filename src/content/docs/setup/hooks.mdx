## The weak spot it targets

**The [agent](../../glossary/#agent) can fail to follow a rule.** An [instruction file](../../glossary/#instruction-file) is advice, and nothing forces the agent to follow it. This is a principle: the guide's runs did not test how often an agent skips a rule. A [hook](../../glossary/#hook) is a script the [harness](../../glossary/#harness) runs at a fixed point. The agent cannot decide to skip it for the tool calls the hook matches. A hook can still be misconfigured, and by default a hook that fails with an exit code other than 2 lets the action go ahead. See [level 4](../../journey/04-trust-but-verify/) and the [hooks shelf page](../../shelf/control/hooks/).

## How it works

A hook has three parts: an event, a script and a reply. The event is a point in the agent loop, such as "before a tool call" or "when the agent stops". The script reads a JSON description of that event on its input. The reply is an [exit code](../../glossary/#exit-code), and sometimes JSON.

The [exit-code contract, `onFailure` and what exit 2 does on each event](../../shelf/control/hooks/#exit-code-2-by-event) are on the shelf hooks page. Exit 0 means the script succeeded; its JSON can still deny a PreToolUse call. Exit 2 blocks on events that support blocking. By default, other non-zero exits are errors that do not block.

## Why exit 1 is a trap

A new author writes a hook that exits 1 to mean "stop". Without `onFailure`, exit 1 does not block. The action goes ahead. The transcript shows a hook error notice that carries the first line of the hook's stderr, such as its own "blocked" message, so the hook looks like it works. **A hook that cannot block looks like a hook that blocks.** The fix is a test matrix that feeds the hook a bad call and checks that the result is a block. [Chapter 2](../../case-study/ch02-hooks/) builds that matrix with 19 cases: allow, deny and malformed input.

The runner’s input is a hook event on standard input. This is source-derived pseudocode for the kit’s `dispatch.py` entry point:

```text
read standard input
try to parse it as JSON
if JSON parsing fails:
    print "Blocked: the hook event is not valid JSON (...)" to stderr
    exit 2
if the parsed value is not an object: print the error and exit 2
read the hook configuration; if unreadable or invalid: exit 2
run the hook scripts matching the event
```

## A tool error can look like a block

Exit 2 means "block" to the harness. The command-line tool grep, for one, exits 2 when it cannot run. A hook that calls such a tool and passes its exit code on reports an error as a policy block. In my setup a hook once ran a system command with a flag that one operating system rejected. The command exited 2, so the failure looked like policy. This is an anecdote, no log kept. My fix is one adapter that sorts hooks into two kinds. An *advisory* hook that exits non-zero is treated as a crash. The adapter logs it, swallows it, and shows a one-line notice at the next prompt. A *gate* hook may exit 2 on purpose. Only a few of my hooks are gates. Most advise.

## What subagents inherit

- Hooks from settings files, managed policy and plugins run for tool calls made by [subagents](../../glossary/#sub-agent). The hook input says which subagent made the call.
- Subagent start and stop are events too. The matcher is the agent type name.
- A custom subagent can carry its own hooks in its definition. They run only while that subagent is active.
- Custom subagents load the project instruction files. The built-in Explore and Plan agents do not. A custom subagent can opt out with the `omitClaudeMd` field in its definition.

**What my own launcher does not inherit.** My setup has a command that starts a helper from a role file. That helper gets the role file and an optional skill. It gets no hooks and no project instructions. If you use such a launcher, put the shared rules into the brief yourself. [Chapter 7](../../case-study/ch07-orchestrator/) builds a check for this.

## Hooks that reinforce behaviour

**Status.** Runs in my setup, in Claude Code. The case study does not build these hooks.

My hooks do two jobs. A guardrail blocks an action. A nudge adds a short note to the agent's context and lets the action go ahead. Most of my hooks are nudges, because a nudge that misfires costs a sentence of context, and a block that misfires stops the work.

Three guardrails cover the shell and the sub-agents:

- A Bash timeout check makes sure each shell command runs with a time limit.
- A wrapper keeps the full output of a failed command that was piped into tail. The [shelf hooks page](../../shelf/control/hooks/#a-pipe-into-tail-hides-the-exit-status) explains the trap.
- A worktree check blocks a [sub-agent](../../glossary/#sub-agent) that would write files from starting in the shared checkout. It must run in its own [worktree](../../glossary/#worktree).

The nudges target habits an agent drops when nothing reminds it. Each row runs at the event named in its first column.

| Event | What it checks | Block or nudge |
| --- | --- | --- |
| After each tool call and each prompt | Five, then ten, tool calls in a row with no [delegation](../../glossary/#delegation) | Nudge |
| After each tool call and each prompt | Ten tool calls in a row with no question to the user | Nudge |
| Each prompt | A claim in the last reply that hedges and was not checked | Nudge |
| After the first markdown write | Nothing: it adds the style guide once per session | Nudge |
| Every N prompts | Nothing: it adds the facts file again, so it survives a long session | Nudge |
| Each prompt | Three or more open questions, which suit a form better than chat | Nudge |
| After each tool call and each prompt | File writes with no test run since | Nudge |
| Before compaction, and at the start after it | Nothing: it saves the [ledger](../../glossary/#ledger) and gives it back after compaction | Nudge |
| Before a delegation | The outgoing brief, checked against stored memory | Nudge |
| Before a push or a pull request | More than 400 changed lines or more than 8 files | Nudge |
| Each prompt | Hooks that crashed since the last prompt | Nudge |
| Stop | Durable facts from the session that were not saved to memory | Blocks the first Stop once |
| Stop | Changed files that no reviewer has read. It starts a read-only [reviewer](../../glossary/#reviewer) | Blocks one Stop per change set |
| Stop | File and line citations that no longer resolve | Blocks until they resolve |

A Stop block that fires once and then lets go is still a block. Give it the same test matrix as a guardrail.

## One set of hooks for several agents

**Status.** Runs in my setup for Claude Code. The Codex CLI wiring is incomplete, and I am repairing it.

Each agent sends hook events in its own JSON shape. I keep one set of hook scripts and one small adapter per agent:

1. The agent calls its adapter with the event.
2. The adapter converts the agent's JSON into one shared event shape.
3. The adapter runs each hook script for that event and merges their output into one reply.
4. If a hook script crashes, the adapter logs it and carries on. The crash report hook names it at the next prompt. This is the advisory rule from [the section above](#a-tool-error-can-look-like-a-block).

Only an exit-code block travels between agents. A JSON deny decision has a shape that each agent defines for itself. An adapter that drops that JSON on the way back allows the action, and nothing says so. So my guardrails block with exit code 2 and a reason on stderr.

In my setup today, Codex CLI wires only the session-start hooks. The blocking guardrails protect Claude Code sessions only. A Codex session runs with no guardrail until the repair lands.

Codex CLI behaviour: hooks are on by default. A hook can block a pre-tool call with exit code 2 and a reason on stderr. Codex skips a new or changed hook until you review and trust it, so the repair needs that review step for each hook.

## End-to-end flow

Rule: "Never force-push." This is one rule, taken through every step.

1. You write the rule in plain English in the instruction file, so the agent can explain it.
2. You write a before-tool hook for shell calls. The script reads the call from its input.
3. The script looks for a force flag on a push. If it finds one, it prints the reason and exits 2. If the input is not valid JSON, it exits 2 as well, because a gate should fail closed.
4. You write the test matrix: one allowed push, one denied force-push, one malformed input. Each has an expected exit code.
5. You run the matrix and see all three pass.
6. You break the hook on purpose, for example by changing the flag it looks for. The deny case must go red. This is the proof that the test can fail.
7. You register the hook in the shared settings file. You test it with a real session.
8. A subagent tries the same push. The hook runs for the subagent too, and the call is blocked.

## What this does not do

A hook covers only the paths it sees. A script that the agent writes and then runs can take actions the hook never matched. A hook is a strong control for the calls it covers, not a promise about everything.
