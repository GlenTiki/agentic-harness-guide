## The weak spot it removes

**Keyword search misses the point.** A search for "stop duplicates" can miss a note titled "count each month once". The words differ and the meaning is the same. Better ranking finds the right note. The aim is to load fewer [tokens](../../glossary/#token) and the right ones.

## Four ways to score a note

| Method | How it scores | Cost |
| --- | --- | --- |
| BM25 | Counts matching words. Rare words weigh more. It is a fixed formula. | Very low. No model. |
| Dense embeddings | Turns the query and each note into number lists, then compares them. Finds similar meaning. | Needs an embedding model. Each text is encoded once. |
| Rank fusion | Merges two ranked lists into one. | Trivial. |
| Cross-encoder | Reads the query and one note together and gives a score for the pair. | Slower. It runs once per pair. |

A [bi-encoder](../../glossary/#embedding) such as the embedding model encodes each text on its own. A [cross-encoder](../../glossary/#cross-encoder) reads the pair together. The pair reading is more precise and slower, so the usual pattern is to run it only on the top results of a faster search.

<p class="verified">Docs page fetched on 2026-10-24: https://www.sbert.net/docs/cross_encoder/usage/usage.html. Quoted line: "Often slower than a Sentence Transformer model, as it requires computation for each pair rather than each text". The docs page states no version of its own.</p>

## What I run

Two searches run on the notes and each returns a ranked list.

1. A BM25 keyword search, top 50.
2. A dense search by cosine similarity on embeddings, top 50.

Then reciprocal rank fusion (RRF) merges the lists. A note scores `1 / (k + rank)` in each list, and the two scores are added. I use k = 60 and give both lists equal weight.

A final small step multiplies the score by a recency boost. The boost grows with how often a note was recalled and fades with a half-life of about 30 days. My code caps it near six percent. It can settle a tie. It cannot overturn a clear match. That is my setting, chosen by judgement, not measured.

### Why the hooks use keyword search only

A per-prompt hook runs on every prompt. Loading an embedding model each time is slow. I have no measurement of what dropping the dense step costs in my setup. Treat the keyword-only choice as a design principle (a cheap step on every prompt), not as a result. The measured table below is the only evidence on the guide for dense search.

A separate retrieval hook runs the fuller search that adds the dense step. It keeps a short per-prompt cache and sits behind a capability switch, so it runs only when the switch is on and enough memory is free. I can also call the fuller search by hand. When free memory is low, the retrieval hook falls back to keyword search and a plain file list.

## Where a cross-encoder would fit

Put it after fusion. Take the top 10 to 20 results. Score each pair. Re-order. Keep the top few.

```text
query → BM25 + dense → fusion → top 20 → cross-encoder → top 3 → prompt
```

A cross-encoder costs more per query, as the documentation above says. It might raise precision. You must measure both on your own notes. The case study gives you an evaluation set and a before-and-after score. Precision@k is the share of the top k results that a person marked relevant. Hit@k is the share of queries with at least one relevant note in the top k. MRR is the mean of 1 divided by the rank of the first relevant note.

## What I will and will not claim

- The cross-encoder API takes pairs and returns one score per pair. It can also rank a list of passages. This is documented.
- Small re-rankers exist, and one is about 22 million parameters. A larger multilingual one is about 0.6 billion, so it is much heavier.
- I measured one small cross-encoder on one laptop CPU. The numbers are in the next section. They say nothing about other machines.
- I do **not** claim identical scores across machines. A cross-encoder uses no sampling, so it should repeat on the same setup, and it did on mine. Floating-point differences can change scores across hardware, batch sizes or library versions. That part is reasoned, not tested.
- I do **not** claim a cross-encoder helps your notes. On my set it did not raise hit@3.
- Ollama had no native re-rank endpoint at the last check, so run the re-ranker through a library or another runtime.

1. The cross-encoder raises MRR, from 0.643 to 0.803, and leaves hit@3 at 0.794. It puts the first correct note higher. It does not find more correct notes.
2. Dense retrieval won on this set. It found a correct note in the top three for 32 of 34 queries. BM25 did so for 27.
3. The hybrid scored below dense alone. I did not investigate why. My own setup chose its fusion by judgement and has not measured it.
4. With 34 queries, one query moves hit@3 by 0.029. The set was built to use other words than the notes, so it favours meaning-based methods. It does not show that dense retrieval is better in general.

**Latency.** I timed the cross-encoder on an Apple silicon laptop under load, CPU only, 4 threads, `sentence-transformers` 6.2.0. The two stored runs (5 and 10 repeats) gave medians of 0.0295 and 0.0233 seconds and maxima of 0.0834 and 0.0823 seconds to re-rank 20 candidates for one prompt. Loading the model took 7.37 and 6.29 seconds. This is a rough size on one machine, not a benchmark ([latency.txt](https://github.com/GlenTiki/agentic-harness-guide/blob/main/examples/retrieval-eval/outputs/latency.txt)). The scores were identical over 10 repeated runs (same file).

## End-to-end flow

1. You collect 20 real prompts from your own work and mark which notes are relevant to each.
2. You run keyword search alone and score precision@3.
3. You run keyword search plus the dense search with fusion and score again.
4. You add the cross-encoder on the top 20 and score again.
5. You time each variant on your machine, with the model already loaded and with a cold start.
6. You keep the cheapest variant that gives the precision you need.
7. You prove the evaluation can fail: shuffle the relevance marks and confirm the scores drop.

## Diagnose a miss

Before you add a re-ranker, find out whether the right note was retrieved at all. [Diagnosing retrieval failure](../../shelf/context/diagnosing-retrieval-failure/) separates "retrieved wrong" from "ranked wrong" and covers a similarity floor and an index that refuses a changed embedder.
