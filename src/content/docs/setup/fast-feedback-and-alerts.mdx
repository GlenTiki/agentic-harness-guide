## The weak spot

**You find out late.** A check that runs at commit time shows its red minutes after the mistake. A log that stops growing looks the same as a quiet system. An alert that says "error" tells you nothing about what to do. This page takes seven practices from ordinary debugging, monitoring and alerting and shrinks each to a size a single maintainer can run. They are common engineering practice. This page makes no measured claim about how often any model fails.

## Seven practices

### 1. Watch mode

**Practice.** A tool watches your files and re-runs the checks on every save. Many test runners and dev servers do this.

**Why it works.** The red appears seconds after the edit, while you still remember what you changed.

**Cheap version.** Poll the modification time of each file, wait a moment for a burst of saves to settle, then run one command. The example below does this in one short script.

*Runs in my setup:* the dashboard reloads on a source change, in both the frontend dev server and the ASGI server. *Built in this page's example:* the watch loop.

### 2. Make a failure reproducible

**Practice.** A failure you can repeat is a failure you can fix. Give it one command, the same input and a saved log.

**Why it works.** A bug you can replay stops depending on memory and luck.

**Cheap version.** When a hook fails, save the exact input it received next to the log line. Then `python3 -I hook.py < saved-input.json` replays the failure. [Chapter 2](../../case-study/ch02-hooks/) builds a hook test matrix in the same spirit.

*Design only* on this page. The example saves no hook input.

### 3. Structured logs with a correlation id

**Practice.** Write one JSON object per line. Give every line a time and a correlation id, a short string made once at the start of a task and repeated on every line.

**Why it works.** One agent run then reads as one thread. You can `grep` the id and see the whole story in order.

**Cheap version.** Use UTC to the second, ending in `Z`, such as `2026-10-25T09:00:30Z`. This is the shape that [chapter 10](../../case-study/ch10-monitor/) uses.

*Design only* here. The fixture logs in the example carry a `run` field, and nothing reads it.

### 4. Liveness versus freshness

**Practice.** Liveness asks whether the process is running. Freshness asks whether it did anything recently. A dead-man's switch is a check that goes red when an expected signal stops.

**Why it works.** A crashed monitor writes no error. It writes nothing, and a green light that nobody updates stays green.

**Cheap version.** Have the system append a heartbeat line on a timer. Then check that the newest line is younger than a limit. This is the [freshness check from chapter 10](../../case-study/ch10-monitor/), cut to one file.

*Built in this page's example:* the stale-log check. Writing the heartbeat line is left to you.

### 5. Alert on symptoms, not causes

**Practice.** Alert on what a user would notice, such as "no run finished today". Do not alert on every internal cause, such as "one retry happened". Every alert says what broke, since when, and the first command to run.

**Why it works.** A symptom alert catches causes you did not predict. A runbook line turns an alert into an action.

**Cheap version.** Print three things on one line: the symptom, the time it began, and a command. The example prints `STALE: last event <time>, limit <n>s`. A runbook line would add `Run: tail -5 run.jsonl`.

*Design only* beyond that one line.

### 6. Keep alerts rare and actionable

**Practice.** Alert fatigue is a known problem in operations work. People stop reading a channel that cries wolf. Teams use severity levels, de-duplication (one alert for a repeated fault), quiet hours and a regular review of noisy alerts.

**Why it works.** An alert that is rare keeps its meaning.

**Cheap version.** Keep two levels: act now, and read later. Send a repeated fault once. Once a week, delete or fix every alert that nobody acted on.

*Runs in my setup:* resource alerts for memory, swap and processor load go to a queue file that I read at session start. *Design only:* the severity levels, de-duplication and weekly prune.

### 7. Close the loop

**Practice.** Every alert that fired is evidence about a weak spot. Feed it to a retro.

**Why it works.** An alert that is fixed and forgotten fires again.

**Cheap version.** After an alert, write what it was, what happened and what you would have preferred, as in [Retros](../retros/). Then follow the [weak-spot loop](../../method/the-feedback-loop/): change a hook, a check or a rule, and keep the alert if it still earns its place.

## Mistakes people make

**Alerting on everything.** It feels safe, so you add one alert per error. Within days nobody reads them. Alert on symptoms and prune weekly.

**A green light with no clock.** A status that shows only a value cannot tell fresh from old. Show the time of the last event beside it, and check the age.

**A check that cannot fail.** A watch loop or a stale-log check that you never saw go red may be wired to nothing. Feed it the stale fixture on purpose.
