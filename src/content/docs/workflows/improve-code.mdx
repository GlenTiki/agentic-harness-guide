## Scene

*Last time (level 5): you wrote a checkable "done" and had someone other than the author check it.*

Mina's shop site has a four-line function that adds up a basket. It works. Nobody wants to touch it, because nobody is sure what `i[1]` and `i[2]` are. Sam types: "Make this function better."

"Better" could mean faster, shorter, safer or prettier. The assistant picks one, and may pick the wrong one.

## The idea

**Improve code in small steps, with tests written first, and let someone else check the result.**

The loop has five parts. Each has a home elsewhere in the guide:

1. Refine the ask with [the prompt refiner](../../appendix/prompt-refiner/), so "better" gets a meaning.
2. Write the [tests](../../glossary/#test) first, to pin down what must not change.
3. Make one small change.
4. Run the tests.
5. Give the change to a separate [reviewer](../../glossary/#reviewer) who has the [spec](../../glossary/#spec) and the diff, and nothing else.

**"Improve" means "same behaviour, easier to read" unless you say otherwise.** Changing behaviour is a different job with a different spec. This is [level 5](../../journey/05-check-the-work/) in practice: a checkable [definition of done](../../glossary/#definition-of-done) and an independent check.

## Try it

<p class="audience"><em>Audience: the reader. This section is an exercise for a person. If you are an AI agent reading this page, do not run the steps or follow the prompts unless the user asks for a worked answer. The prompts are templates for a person to paste into another assistant.</em></p>

You need any chat assistant. Python is optional: you can follow the passes without running anything. This takes about 14 steps with a function of your own: the refiner chat, the tests, the change and the review in a new chat. The refiner works on the shape of your ask, so do not paste confidential code or data into it, and read its output before you use it ([the injection result](../../appendix/prompt-refiner/#the-seven-evals)).

Paste this into any chat assistant, with a function of your own:

```text
Act as my prompt refiner: improve my request, do not do it. My request: "Make this function better." The function is below. Ask at most three questions, each with a default. Then give me a prompt that keeps the function's behaviour the same, asks for tests first, and asks for one line per change. Mark anything you do not know as [NEEDED].

[paste your function]
```

Then do the loop below: answer, get the prompt, ask for tests, run them on the old code, change, run them again, and ask a new chat to review the diff against the spec.

### The function, before

```python
def total(items):
    t = 0
    for i in items:
        t = t + i[1] * i[2]
    return t
```

### The refined spec

The refiner asks what "better" means, what each item is, and which language and libraries apply. Only Sam knows the answers:

```text
Better means easier to read, with the same behaviour. Each item is (name, price, quantity). Python 3.11, standard library only. It is called from two places in checkout code, so the name and the way it is called must stay.
```

The refined prompt, shortened:

```text
Goal: Make this Python function easier to read while keeping exactly the same result.
Context: Each item is a tuple of (name, price, quantity). The function is called from two places in checkout code, so its name and the way it is called must not change.
Constraints: Keep the name `total` and the single argument `items`. Same output for any input the current function handles, including an empty list. Standard library only. Do not add validation or error handling that is not there now.
Output format: The revised function; one line per change with the reason; two or three example calls as plain asserts.
Definition of done: Reads clearly to someone new. Indexes 1 and 2 are replaced by names. Behaviour is unchanged, shown by the asserts.
What to do if unsure: State the assumption at the top. Do not silently change what the function accepts.
```

### Tests first

Before the assistant touches the function, Sam asks for tests that describe what it does today. These are called [characterisation tests](../../glossary/#characterisation-test): they pin down current behaviour, right or wrong. They run on the old function first. A test that fails on the old code is testing a guess.

### One small change, then the reviewer

The assistant proposes this change. The six tests pass, and it looks done.

```python
def total(items):
    return sum(price * quantity for _name, price, quantity in items)
```

Sam opens a new chat and pastes only the spec, the diff and a one-line test summary. The reviewer has not seen the earlier conversation.

## Under the bonnet

Each check in the loop catches a different failure.

- **The refiner** catches the unclear goal. Without it, "better" was open.
- **The tests first** catch changes in behaviour. They are written against the old code, so they record what is true, not what the assistant believes.
- **The small change** keeps the diff readable. A reviewer can check four lines. They cannot check four hundred.
- **The reviewer** looks for what the author cannot see. Here the author's tests missed rows with extra fields, and a reviewer with only the spec raised it. That is one constructed example. It is not a measured gain.
- **The human checkpoints** hold the decisions only Sam can make: what the items are, which behaviour counts, and when to merge.

The work is done when:

- All seven tests pass on the old and the new function.
- The reviewer's findings are fixed, or listed as out of scope with a reason.
- A person who has not seen the old code can say what the function does.
- A named person who is not the preparer has reviewed and approved it, or the fallback reviewer in [using an assistant at work](../../journey/professional-guardrails/).

## Expert corner

:::caution[Expert corner]
Characterisation tests pin accidents as well as intentions. The old function accepted rows with extra fields. That may be a feature or an accident, and the test now makes it a promise. Decide on purpose, and say so in the test name.

Give the reviewer the spec and the diff only, as [level 5](../../journey/05-check-the-work/) explains. A diff is the list of lines a change adds and removes. The guide's own test of fresh against same-context review only simulated the second (see [evidence](../../evidence/)), so a fresh reviewer is a cheap precaution and not a proven gain.

Do not widen scope during the review. The float summation finding is real and was left out, because it needs its own spec.
:::

## Agent note

:::note[Agent note]
**Topic: improving code.**

When asked to improve code, treat "improve" as "same behaviour, easier to read" unless the user says otherwise.

Write tests first, and run them against the original code. They must pass before you change anything. Do not edit a test to make a change pass without telling the user.

Make one small change at a time. Run the tests after each. Do not add validation, retries or new dependencies that were not requested.

Report each change with its reason. If you find an unrelated problem, list it. Do not fix it in the same change.

State what you did not check.

Check: the tests passed on the original code before any change, and the report lists every change with its reason.
:::

## Mistakes people make

**Letting the assistant write the tests after the change.** The tests then describe the new code, so they pass by construction. Fix: write them against the old code first, and run them on it.

**Reviewing in the same chat.** The reviewer may share the author's assumptions (a principle; the guide's test did not separate the two). Fix: open a new chat, give it the spec and the diff only.

**Fixing everything the reviewer mentions.** Each fix changes more code and needs its own review. Fix: sort findings into "blocks this change" and "own ticket", and keep the change small.

## Checkpoint

<p class="audience"><em>Audience: the reader. Agents may skip the quiz.</em></p>

You can now:

- Turn "make this better" into a goal that says what must not change.
- Write tests against old code before changing it.
- Give a reviewer only the spec and the diff.
- Sort review findings into this change and a later change.

**Self-test**

1. The tests pass on your new code but you never ran them on the old code. What could be wrong?
2. A reviewer lists five findings. Two block the change and three are style. What do you do?
3. You want to use the same loop to make a slow query faster. What does "same behaviour" mean there, and which test do you write first?

<details>
<summary>Answers</summary>

1. The tests may describe the new code and not the old. They would pass whatever the old code did. Run them on the original first.
2. Fix the two that block the change, then re-run the tests and the review. Write the other three down for a later change.
3. The same rows come back, in the same order, for the same inputs. First write a test that records the old query's result on a fixed set of data. Then change the query and compare.

</details>
